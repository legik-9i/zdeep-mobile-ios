# Стабильные local-тесты и сохранение диагностики testing — план исправления

> **Для исполнителя:** выполнять задачи по чекбоксам через `superpowers:executing-plans` либо `superpowers:subagent-driven-development`. Пользователь выбрал subagent-driven-development и разрешил выполнение 2026-10-09.

**Цель:** Сделать автоматические тесты воспроизводимыми исключительно в local, требовать успешной подготовки local-сервисов и сохранить отладку реального iPhone в testing.

**Архитектура:** Сохраняем существующие наборы `unit`, `integration`, `ui`, `all` и проектный Python CLI. Тестовые targets используют одну подписанную Simulator-сборку; контур testing остаётся в командах диагностики. Unit-фикстуры изолируем существующими fake-адаптерами, проверки реального storage/WebKit оставляем интеграционными сценариями.

**Технологии:** Python `unittest`, Xcode `build-for-testing`/`test-without-building`, Swift Testing, XCTest UI, WKWebView, существующие фикстуры.

**Основание:** Согласованные в чате требования 2026-10-09; полный контракт приведён ниже. Исходная ветка `main`, коммит `8df775f`. Отдельная спецификация для этой ограниченной правки не создаётся.

## Согласованный контракт

- Все автоматические тесты выполняются в `local`. `test --environment test` и сетевой `preflight --environment test` больше не поддерживаются.
- Testing используется для отладки: сохраняются `device-install`, `device-launch --environment test`, `diagnose --target device --environment test`, `logs` и simulator-диагностика local/test.
- На iPhone сохраняются штатная подпись проекта, `ZDEEP_ENVIRONMENT=test`, opt-in USB mailbox и ручное открытие WebView. Health для testing не нужен, запрос к корню test API для оценки доступности не выполняется.
- Local API проверяется через `GET /health`, local Web — через `GET` настроенного адреса. Требуется HTTP 200; 401/403/404/5xx, тайм-аут и транспортная ошибка блокируют сетевой прогон.
- Unit и тесты Python runner'а не требуют живых API/Web. Отрицательные HTTP-фикстуры проверяют обработку ошибок; ответы реальных сервисов с ошибками не считаются успешной подготовкой.
- Новые типы прогонов, зависимости и параметры конфигурации не добавляются. `all` уже включает три iOS-набора; после успешного `all` отдельно их не повторяем.
- В ходе работы выполняются относящиеся к изменению лёгкие тесты. Отдельный UI/integration тест запускается раньше финала только для воспроизведения конкретной проблемы или проверки её исправления.
- Полный local `all` выполняется в финале. Для этой задачи один дополнительный `all --skip-build` оправдан проверкой повторяемости и повторного использования сборки. Это не новый обязательный повтор для всех будущих задач.
- Документация на русском; запросы к prod запрещены. Код приложения и протокол бриджа не меняются без доказанной необходимости.
- До выполнения проверить статус рабочей копии и сохранить чужие изменения. При выборе SDD применять AGENTS.md: реализация/исправления Luna, ревью Sol, Astra запрещена. При выборе выполнения в текущей сессии это правило выбора моделей не применяется.

## Что установлено, а что ещё предстоит подтвердить

- После разрешённого доступа к CoreSimulator завершённый local `all` прошёл: 256 тестов, 0 падений и пропусков.
- Лишний прогон `test/all` собрал приложение без подписи: 9 тестов упали; прямые Keychain-ошибки имели статус `-34018`, остальные падения зависели от восстановления/очистки storage. Отдельного контрольного подписанного test-прогона не было; после принятого ограничения local он не нужен.
- Python-тест `test_ad_hoc_signing_is_limited_to_local_unit_simulator_builds` закрепляет различие подписей, а инструкции требуют переиспользования сборки между контурами. Эти правила противоречат друг другу.
- Fingerprint обходит все файлы `scripts`, включая существующий `__pycache__/*.pyc`: это подтверждённый источник нестабильной идентичности кэша.
- Часть unit-тестов координатора вызывает настоящий общий очиститель. Он удаляет общий WebKit storage и содержимое каталога временных файлов, поэтому может затронуть данные других асинхронных тестов. Это риск, обнаруженный по коду, а не доказанная причина уже наблюдавшегося flaky-падения.
- `@Suite(.serialized)` интеграционных тестов упорядочивает эту suite, но не защищает её от других suites. Не лечить общие данные добавлением `.serialized` в каждую suite.

## Фокус ревью

1. `test`/`preflight` с контуром testing отклоняются до любых внешних вызовов; команды диагностики testing по-прежнему принимаются. Проверки в задаче 1.
2. `build-tests` создаёт сборку, годную для последующих `unit/integration/ui/all --skip-build`; bytecode не меняет fingerprint, исходники меняют. Проверки в задаче 1.
3. API или Web отвечает 404/другой ошибкой: нет вызова build/test и нет успешного сообщения CLI. Unit обходится без сетевой проверки. Проверки в задаче 2.
4. Unit-очистка не удаляет чужую фикстуру или данные WebKit; реальный Keychain продолжает проверяться отдельными адаптерными тестами. Проверки в задаче 3.
5. Код 65, неполный/пустой xcresult, Failed или неожиданный Skipped не становятся зелёным результатом; путь проблемного bundle доступен для разбора. Проверки в задаче 1 и финальная приёмка.

## Передача и критерии завершения

- CLI и `BuildManager` отклоняют автоматический testing-прогон до внешних действий.
- Диагностика реального устройства по-прежнему выбирает testing, сохраняет штатную подпись и mailbox.
- Local network-preflight не принимает 404 и другие ошибочные ответы; unit не зависит от сети.
- `build-tests`/`test` создают совместимую подписанную сборку, не инвалидируемую Python-кэшем.
- Все обязательные local-сценарии исполнены, полная приёмка и один повтор зелёные; прямые Keychain-тесты сохранены.
- Нет новых наборов, регулярных двойных полных прогонов, молчаливых skips или retries ради зелёного результата.
- Отчёт различает проверенное выполнение, риски из чтения кода и непроверенную физическую диагностику.

**Самопроверка плана:** требования чата распределены по пяти задачам; все пять пунктов фокуса ревью имеют проверки. Отладочные команды защищены до правок preflight. Не требуется test-health, изменение backend/testing или новая система тестирования. Способ реализации выбран пользователем: subagent-driven-development; реализация Luna, ревью Sol согласно AGENTS.md.
