# ZDEEP iOS: клиент авторизации

Дата: 2026-10-03.

Статус: спецификация по результатам отдельного brainstorming компонента. Решения согласованы в разговоре; письменный документ ожидает проверки пользователя. Реализация и её план пока не начаты.

Связанные документы: [общая спецификация приложения](2026-10-03-mobile-session-design.md), [хранилище привязки](2026-10-03-binding-store-design.md), [контракт bridge](2026-10-03-webview-bridge-prerequisites.md).

## 1. Назначение и границы

Клиент выполняет одну попытку регистрации `pair` или получения JWT `token`: формирует запрос, запрашивает подпись у хранилища, отправляет HTTP-запрос и проверяет ответ. Вызов завершается проверенной сессией, структурированной ошибкой либо отменой.

Сохранение завершённой регистрации выполняет вызывающий компонент через хранилище. Менеджер сессии хранит JWT, объединяет одновременные запросы авторизации и назначает обновления и повторы. Координатор обрабатывает пользовательские действия, показывает ошибки и выполняет сброс. Клиенту не нужны WebView, экраны или постоянное хранилище JWT.

Зависимости: хранилище для подписи, HTTP-транспорт, часы и готовые адреса API из инфраструктуры. Для транспорта используется предложенный в общей спецификации URLSession. Правила окружений и маршрутизации предоставляет инфраструктура.

## 2. Выбранный подход

Согласовано правило «один вызов — одна попытка». В клиенте нет автоматических повторов после сетевого отказа, HTTP-ошибки или расхождения времени. Даже при `TIMESTAMP_OUT_OF_RANGE` текущий вызов возвращает ошибку, а поправка используется следующим вызовом.

Рассмотренный альтернативный подход — включить повторы и сохранение привязки в клиент. Выбранное разделение оставляет бизнесовые решения у менеджера сессии и координатора и предотвращает скрытые повторные `pair`.

## 3. Операции и результат

| Операция | Вход |
| --- | --- |
| `pair` | Описание `pending`-привязки: `bindingId`, `publicCertificate`; `carToken` из QR |
| `token` | Описание `registered`-привязки: `bindingId`, `publicCertificate`, подтверждённый `carId` |

Описание берётся из результата хранилища. Приватный ключ клиенту не передаётся. `bindingId` используется для запроса подписи и проверки актуальности у вызывающего компонента; в HTTP-тело и бизнесовый bridge не входит.

Успешный результат обеих операций одинаков:

- `accessToken` — пользовательский JWT;
- `userId` и `carId` — контекст, подтверждённый ответом сервера;
- `expiresAt` — срок JWT в UTC ISO 8601 для bridge;
- срок действия для нативного планирования, рассчитанный с учётом серверного времени и доставки ответа;
- `serverTime` — время сервера в миллисекундах Unix;
- идентификатор попытки для связи с диагностикой.

Нативный срок задаётся как дедлайн на монотонных часах, общих с менеджером сессии. Это позволяет учитывать время между получением результата и его использованием. `expiresAt` остаётся серверной датой истечения, а не датой, скорректированной под часы телефона.

После успешного `pair` вызывающая сторона сначала сохраняет `registered` через хранилище, затем публикует сессию. Ошибка сохранения не становится успешной регистрацией. После `token` запись привязки не перезаписывается ради нового JWT.

## 4. Формирование и подпись запроса

Локальный референс протокола:

| Метод | JSON-тело |
| --- | --- |
| `POST /auth/mobile/pair` | Только `publicCertificate`, `carToken` |
| `POST /auth/mobile/token` | Только `publicCertificate`, `carId` |

Готовые адреса методов берутся из инфраструктуры; эти пути описывают серверный референс. URL из QR используется для извлечения токена на предыдущем этапе и не становится адресом запроса.

Порядок одной попытки:

1. Создать идентификатор попытки, зафиксировать конфигурацию API и проверить отмену.
2. Один раз сериализовать JSON в UTF-8.
3. Получить текущий timestamp с доступной поправкой часов, представить десятичными миллисекундами.
4. Передать хранилищу `bindingId` и точные байты `<timestamp>|<rawBody>`.
5. Получить подпись ECDSA P-256 с SHA-256 в DER, закодировать в Base64.
6. После проверки отмены отправить тот же JSON с `Content-Type: application/json`, `X-Timestamp`, `X-Signature`.
7. Получить полный ответ, проверить отмену, HTTP-статус и содержимое.
8. В общей сериализованной процедуре завершения проверить актуальность вызова и конфигурации, применить допустимую поправку часов и вернуть один итог операции.

JSON не сериализуется повторно после подписи. Новый вызов получает новый timestamp и подпись. Хранилище отклоняет подпись для устаревшего `bindingId` или `resetting`; такой запрос не отправляется.

Для обоих методов транспорт не следует HTTP redirects автоматически, включая 307/308. Исходный ответ 3xx возвращается как отказ сервера с сохранением статуса. Подписанный POST не отправляется повторно по адресу из `Location`. Это правило является частью контракта транспорта одной попытки и не меняет маршрутизацию инфраструктуры.

## 5. Проверка успешного ответа

Текущий сервер возвращает HTTP 200 и JSON: `accessToken`, `tokenType`, `expiresIn`, `serverTime`, `userId`, `carId`. JWT содержит `userId`, `carId`, `iat`, `exp`, `aud: zdeep-webview`; текущий срок выдачи — 900 секунд. Клиент вычисляет срок из ответа и JWT, а не фиксирует 900 секунд как постоянный клиентский срок.

До возврата успеха проверяются:

- HTTP 200 и корректный JSON-объект;
- непустые строки JWT, `userId`, `carId` и `tokenType: Bearer`;
- конечные корректные значения `serverTime` и положительного `expiresIn`;
- возможность прочитать JWT-контекст и корректный `exp`, согласованность `userId` и `carId` в JWT с JSON-ответом;
- совпадение `carId` ответа `token` с машиной зарегистрированной привязки;
- для `pair` — совпадение машины ответа с `carId` в JWT машины из QR; эти данные QR используются для проверки согласованности, сервер подтверждает подлинность токена;
- положительный оставшийся срок на момент получения полного ответа.

JWT выпускает и подписывает сервер. На телефоне чтение его payload служит проверке структуры и согласованности контекста с ответом API.

Единицы времени: `exp` и `expiresIn` — секунды, `serverTime` — миллисекунды. Расчёт выполняется в миллисекундах:

```text
expiryMs = min(exp * 1000, serverTime + expiresIn * 1000)
httpDurationMs = монотонное время получения полного ответа − время отправки
remainingMs = expiryMs − serverTime − httpDurationMs
deadline = монотонное время получения полного ответа + remainingMs
```

Время доставки консервативно учитывается полной длительностью HTTP-запроса. `expiresAt` представляет `expiryMs` в UTC ISO 8601. При `remainingMs <= 0` результат возвращается как некорректный ответ и не публикуется.

Некорректный ответ не сохраняется и не запускает повтор внутри клиента. Политику при ошибке и сохранённую привязку определяет вызывающая сторона по общей спецификации.

## 6. Ошибки и поля экрана Stitch

Структурированная ошибка содержит категорию, этап операции, идентификатор попытки, HTTP-статус при наличии, полный серверный `code` при наличии и безопасные диагностические сведения локальной ошибки. Пользовательский текст и действия формирует вызывающий компонент.

| Категория | Значение кода в строке экрана, до 15 символов |
| --- | --- |
| Сетевая ошибка | `NETWORK` |
| Таймаут | `TIMEOUT` |
| Отказ сервера | `HTTP_` и фактический статус, например `HTTP_403` |
| Некорректный ответ | `BAD_RESPONSE` |
| Ошибка доступа к ключу | `KEYCHAIN` |
| Ошибка создания подписи | `SIGNATURE` |

Известные и неизвестные серверные коды сохраняются без сокращения. HTTP-отказ остаётся отказом сервера даже при отсутствии пригодного JSON: статус сохраняется, полного серверного кода может не быть. Для HTTP 200 с непригодным содержимым возвращается `BAD_RESPONSE` и полученный статус. Ошибка неактуального `bindingId` обрабатывается вызывающим компонентом как устаревшая операция, без экрана ошибки прежней попытки.

Макет Stitch проверен по HTML экрана `projects/1417382377358815087/screens/411b28d9024448b7a36d813cbf00b56c`. Согласованные поля:

- источник — `NT` для нативной ошибки;
- короткий код — из таблицы, максимум 15 символов;
- идентификатор попытки — 8 шестнадцатеричных символов, создаётся в начале вызова и используется во всех его диагностических событиях;
- версия — фактическая версия приложения, добавляемая экраном;
- объяснение — русская причина с полным серверным `code`, если он есть.

Пример строки: `Код: NT · HTTP_403 · A7C291F0`, рядом версия приложения. В объяснении: «Доступ к автомобилю запрещён. CAR_ACCESS_DENIED». Короткий идентификатор связывает скриншот с локальным диагностическим журналом; он не является серверным идентификатором запроса или гарантией глобальной уникальности.

Клиент пишет события в существующую диагностику, используя тот же идентификатор. JWT, QR-токен, приватный ключ, подписи и полное подписанное тело в логи и текст ошибок не включаются. Формат диагностики хранилища и других нативных компонентов использует ту же схему представления; их категории уточняются в соответствующих спецификациях.

## 7. Поправка часов

Сервер допускает расхождение подписанного timestamp и своего времени не более двух минут. При `TIMESTAMP_OUT_OF_RANGE` возвращает `serverTime`; успешный ответ тоже содержит это поле.

Клиент хранит одну поправку часов в памяти для текущей конфигурации API. Начальное значение — ноль. После принятого успешного ответа или корректного `TIMESTAMP_OUT_OF_RANGE` вычисляет разницу между серверным временем и временем телефона при получении ответа. Следующий timestamp равен текущему времени телефона плюс поправка. Это приближённая оценка с погрешностью доставки ответа; она не является отдельным сервисом синхронизации часов.

Отменённый или устаревший вызов не меняет поправку. Другие ошибочные ответы её не меняют. При создании нового клиента или замене конфигурации API поправка сбрасывается. На диск она не сохраняется, системные часы телефона не изменяются.

Изменяемое состояние клиента и финальная процедура завершения находятся на `MainActor` вместе с менеджером сессии. Остановка менеджера синхронно инвалидирует вызов в этой же области до отмены сетевой задачи; возврат HTTP и применение поправки выполняются только после проверки актуальности там же. Синхронные операции Keychain/подписи остаются в отдельном сериализованном хранилище; асинхронный HTTP не блокирует главный поток. Собственная параллельная очередь поправки часов и отдельные locks для неё не нужны.

Актуальность обеспечивается внутри процедуры завершения, до изменения поправки. Вызывающая сторона обязана отменить текущий вызов перед сбросом или заменой привязки, заменой конфигурации API либо запуском другой попытки вместо прежней. Сигнал отмены инвалидирует вызов в той же сериализованной области, где клиент завершает операции и изменяет поправку. Замена конфигурации также инвалидирует прежний вызов и сбрасывает поправку в этой области. Между финальной проверкой, применением поправки и фиксацией результата другая операция не вмешивается. Правило одинаково для успешного ответа и `TIMESTAMP_OUT_OF_RANGE`; одной проверки вызывающей стороной после возврата результата недостаточно.

Исправление времени не повторяет текущий запрос. `TIMESTAMP_OUT_OF_RANGE` возвращается с HTTP-статусом и полным кодом. Следующую попытку запускает пользователь либо менеджер сессии согласно общей политике. Первичный `pair` не получает скрытого повтора.

Этот приём применяется в протоколах подписанных запросов, например AWS SDK; он не является отдельным стандартом iOS. Механизм хранения поправки — решение этого клиента.

## 8. Таймаут и отмена

Полный HTTP-запрос ограничен 30 секундами с отправки до получения всего ответа. Это общий предел длительности, включая ожидание связи и передачу данных, а не только пауза между получаемыми порциями. Подготовка JSON и подпись происходят до начала HTTP-таймаута.

В URLSession `timeoutIntervalForRequest` ограничивает ожидание новых данных и сбрасывается при их поступлении. Реализация также обеспечивает общий предел всей загрузки через `timeoutIntervalForResource` либо эквивалентный монотонный дедлайн. Сетевой запрос при достижении предела прекращается и возвращает `TIMEOUT`. Таймаут остаётся таймаутом, даже если технически прекращение транспорта выдаёт код отмены.

При приостановке процесса iOS своевременный возврат результата вызывающему компоненту не гарантируется. После возобновления проверяется фактический дедлайн незавершённого запроса; просроченная операция завершается таймаутом до применения позднего результата. Завершённый до приостановки и уже проверенный результат обрабатывается обычными правилами приложения.

Пользовательская отмена отдельно от ошибки: прекращает подготовку или активный сетевой запрос, завершает вызов результатом «отменено». Проверки отмены выполняются между этапами подготовки и перед возвратом результата. Уже выполняющийся синхронный вызов хранилища может завершиться, но после отмены его результат не используется для отправки запроса.

Поздний сетевой ответ отменённого вызова не возвращается как сессия и не обновляет поправку часов. Координатор и менеджер сессии дополнительно проверяют актуальность попытки перед применением результата. Действующий запрос и его отмена имеют один итог, определяемый сериализованным завершением; два результата одной попытки не публикуются.

Клиент оставляет очистку привязки координатору. Сервер мог принять запрос до отмены и сохранить свою запись; локальная отмена её не отзывает. Уже полученный результат, отменённый затем на этапе ожидания WebView, обрабатывается правилами сброса общей спецификации.

## 9. Требования к будущей проверке

Это требования для плана реализации, а не отчёт о выполненных тестах:

1. Каждый вызов отправляет не более одного запроса авторизации; HTTP-ошибки и поправка времени не вызывают повторного `pair`.
2. Сервер принимает публичный ключ, подпись и точные байты обоих методов; повторная сериализация не меняет отправляемое тело.
3. Оба метода возвращают одинаковый проверенный результат; `pair` сам не сохраняет `registered`.
4. Пустой JWT, некорректный срок и несовпадающая машина или JWT-контекст дают `BAD_RESPONSE`.
5. HTTP-отказ сохраняет статус и полный серверный код, включая неизвестный; ответ без JSON сохраняет статус.
6. Все короткие коды помещаются в 15 символов; идентификатор на экране совпадает с событиями этой попытки, версия берётся из приложения.
7. Корректный `serverTime` меняет timestamp следующего вызова; текущий отказ по времени остаётся ошибкой одной попытки.
8. Поправка и расчёт срока учитывают серверное время; токен не получает лишнего срока из-за задержки ответа или неверных часов телефона.
9. Общий 30-секундный дедлайн не продлевается постепенным поступлением данных. После возобновления приостановленного процесса просроченная незавершённая операция даёт таймаут до применения позднего результата.
10. Отмена до подписи, во время подготовки и после отправки не публикует сессию, не обновляет поправку и не показывает пользовательскую ошибку.
11. Гонка ответа с отменой или таймаутом имеет один итог; неактуальная привязка не подписывает новый запрос. Отмена и смена конфигурации до завершения исключают изменение поправки и успешным ответом, и `TIMESTAMP_OUT_OF_RANGE`.
12. Перезапуск процесса начинает с нулевой поправки; JWT, поправка и QR-токен не восстанавливаются с диска.
13. HTTP 307/308 и другие redirects возвращаются исходным отказом сервера; транспорт не отправляет подписанный POST по `Location`.
14. Расчёт срока использует единицы из формулы: ответ с `expiresIn = 900` даёт срок порядка 900 секунд с вычетом доставки, а не порядка 900 миллисекунд.

Проверки используют уже настроенную инфраструктуру, заменяемые транспорт и часы, а для совместимости подписи — реальный серверный референс.
