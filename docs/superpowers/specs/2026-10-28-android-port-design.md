## 1. Цель и результат

Получить работающее Android-приложение со всем пользовательским функционалом текущего iOS-приложения. Android — дополнительная платформа; пользователь получает один завершённый результат, хотя реализация и проверки выполняются постепенно.

Результат поставки: устанавливаемый `testingDebug.apk`, исходники, воспроизводимые команды сборки и конфигурация `productionRelease` для будущего выпуска. По уточнению пользователя production APK в этой задаче не собирается, включая unsigned-вариант. Публикацию в RuStore, оформление магазина и последующий выпуск пользователь выполняет сам. Производственный ключ подписи предоставляется позже, не требуется для начала или завершения этой задачи и не создаётся исполнителем. Конфигурация Release предусматривает внешний keystore и параметры подписи вне репозитория; фактическая release-сборка и подпись остаются непроверенными до будущего выпуска.

Подтверждено пользователем:

- Android 11 и новее (`minSdk = 30`), распространение через RuStore, Kotlin и Jetpack Compose.
- Функции и качество сохраняются; системные элементы, разрешения и взаимодействия могут выглядеть по Android.
- Обычные телефоны работают в портретной ориентации.
- Общие с iOS веб и backend; iPhone и Android независимо привязываются к одной машине и могут работать одновременно.
- После удаления приложения или переноса на другой телефон необходим новый QR.
- Debug-панель, произвольное выполнение JS с компьютера и специальный диагностический mailbox не нужны. Firebase и нативный Sentry не добавляются; остаётся существующий вебовый Sentry.
- Существующие иллюстрации загрузки сохраняются; ThinkingOrb заменяется штатным Android-индикатором.
- Для Android используется тема Stackflow `android`, для iOS остаётся `cupertino`.
- Android Back передаётся вебу: закрыть верхнее модальное окно, иначе вернуться по Stackflow; на корне ничего не делать.
- Доступен только эмулятор. Разработка и автоматические сетевые проверки — local; ручная приёмка пользователя — testing с заранее подготовленным QR в картинке.

## 3. Подход и решения исполнителя

Выбранный в разговоре подход — отдельная нативная оболочка Kotlin/Compose вокруг существующего веба, с переносом логики авторизации и состояний. Coordinator / BindingStore / AuthClient / SessionManager / WebSession / NativeBridge описывают существующие обязанности и источник поведения, а не обязательную копию Swift-классов, протоколов и фабрик. На Android использовать прямые зависимости и штатные средства жизненного цикла; интерфейс вводится только для нужной подмены в тесте или реальных разных реализаций.

Технические решения исполнителя; отдельные продуктовые предложения помечены явно:

- Согласованы `minSdk = 30` (Android 11) и `compileSdk = targetSdk = 36` (Android 16 — основная среда разработки и тестирования); AGP, Kotlin и Compose — совместимый набор, зафиксированный в сборке. Требования RuStore проверяются при настройке Release, без предположения, что правила Google Play автоматически действуют в RuStore.
- Одна Activity, Compose для нативных экранов; обычный Android WebView через `AndroidView`. Не создавать нативный стек для экранов сайта и не добавлять стороннюю WebView-обёртку.
- CameraX и bundled ML Kit Barcode Scanning: распознавание QR без ожидания скачивания модели. Для связки камеры и детектора использовать официальный `LifecycleCameraController` / `PreviewView` / `MlKitAnalyzer`, а не писать свой обработчик кадров. Включить только формат QR. Не использовать сканер, требующий установки модуля через Google Play Services. Версии фиксируются при реализации.
- Для подписанных HTTP-запросов — минимальный отменяемый транспорт, предпочтительно OkHttp с общим deadline 30 секунд, отключёнными redirects и автоматическими сетевыми повторами. Плановые повторы остаются только в SessionManager, как в iOS. Выбор библиотеки не меняет wire-протокол.
- Один applicationId для local/testing/production; окружение задаётся сборкой и определяет адреса API/веба. Отдельные приложения для окружений не создаются. Переход между Debug и Release с разными ключами подписи требует удаления установленной версии и новой QR-привязки; это согласовано пользователем. Граница данных повторяет `AppEnvironment.databaseScope` iOS: `local` отдельно, `testing/production` — общий scope. При установке сборки поверх прежней смена scope требует очистки до восстановления входа; достаточно сохранённого маркера scope, без менеджера нескольких привязок и экранного переключателя окружений.

### Проверка на лишние механизмы (ponytail, 28 октября)

| Задача | Готовое решение / существующий источник |
| --- | --- |

| Системный Back | Штатный Compose `BackHandler`, затем одно событие в существующем host-канале; без ручного распознавания системного жеста. |
| QR | Официальная связка CameraX и ML Kit; текущие правила разбора QR и однократного результата из iOS. |
| Окружения и APK | Gradle product flavors/build types и стандартная подпись; без собственного сборщика и установщика. |

Новый связующий код необходим только там, где готовые части не соединены: Android-транспорт Promise/ответа, передача системного Back существующей веб-навигации и подключение текущих модалов к этой команде. Это локальные адаптеры, не универсальный bridge SDK или новая система модальных окон. iOS-бизнес-правила всё равно придётся перенести на Kotlin; их не заменяют новые продуктовые правила. Hilt/Koin, многомодульная Clean Architecture, отдельная шина событий и инфраструктура «на будущее» задачей не обоснованы.

Соседний `zdeep-agent` подтверждает использование OkHttp в Android-проектах ZDEEP, но его `RequestSigningInterceptor` не подходит для копирования: подписывает `timestamp|version|jsonBody` и при ошибке подписи продолжает запрос без неё. Здесь сохраняется мобильный контракт `timestamp|raw JSON`, а ошибка подписи останавливает запрос, как в iOS.

## 4. Пользовательские сценарии и UI

При старте показывается логотип, восстанавливается привязка. Без привязки — welcome с прежним текстом, иллюстрацией, сканированием и справкой. С привязкой — загрузка с получением JWT и подготовкой веба; welcome не мигает.

QR-сканер использует системное разрешение камеры, принимает один результат и освобождает камеру. Закрытие возвращает на welcome. Обрабатываются отказ, повторный отказ/переход в настройки, системное ограничение камеры и изменение разрешения в фоне. Запоздалый результат старого сканирования игнорируется. Не копировать iOS-категории разрешений буквально, если Android различает их иначе.

После принятого QR показывается случайная одна из восьми иллюстраций. Она стабильна в пределах ожидания, включая фон. Поверх неё штатный индикатор без видимой подписи «Загрузка», с доступным именем для TalkBack. Техническая очистка и короткое ожидание разрешения используют обычную нативную загрузку. На загрузке нет отвязки. Готовый WebView раскрывается растворением верхнего загрузочного слоя; системное отключение анимаций учитывается.

Ошибки сохраняют русское объяснение, серверный код при наличии, короткий диагностический код, идентификатор попытки и версию приложения. Первичная ошибка регистрации даёт «Начать сначала» после завершения очистки; зарегистрированная привязка — контекстный повтор и подтверждаемую отвязку. Ошибка очистки блокирует новый вход до успешного повтора. Нативный код ошибки хранилища может называться `KEYSTORE` вместо iOS `KEYCHAIN`.

Справка открывает `/about.html` текущего окружения в отдельном WebView без бизнесового bridge. Используется Android-шторка с закрытием жестом/системным Back. Обычные ссылки остаются в справке, новые окна передаются браузеру; при ошибке — прежний текст без нового набора функций.

Системные панели, вырезы, клавиатура, масштаб шрифта и TalkBack не должны перекрывать действия. При открытой клавиатуре Back сначала закрывает её; этот Back не вызывает одновременно pop экрана. В нативном сканере/справке Back закрывает соответствующий экран. Во время авторизации/очистки Back не должен скрыто удалять привязку или запускать вторую операцию; поведение нативного контейнера задаётся явно и проверяется тестом.

## 5. Привязка и авторизация

Android генерирует EC P-256 в `AndroidKeyStore`, без обязательной биометрии и без экспорта приватного ключа. Backend получает Base64 DER/SPKI публичного ключа (`publicCertificate`), а не полный X.509-сертификат из Keystore. Подпись — SHA-256/ECDSA, DER, Base64 над точными байтами `<timestamp>|<raw JSON>`. Тело после подписи не сериализуется заново.

Метаданные привязки сохраняются штатным `AtomicFile` в `noBackupFilesDir`: `bindingId`, alias ключа, publicCertificate, `carId`, `pending/registered/resetting`. Доступ к метаданным/ключам сериализован: `AtomicFile` не обеспечивает блокировку сам. Создание ключа и запись файла не являются одной транзакцией: восстановление должно удалять незавершённые app-owned aliases и остатки pending/resetting, не затрагивая чужие ключи. Ошибка чтения или отсутствующий ключ при зарегистрированной записи не считаются автоматически чистой установкой: экран ошибки с повтором/подтверждённым сбросом.

JWT остаётся только в памяти native и текущего веб-документа; не сохраняется в файлы, backup, SavedStateHandle, Bundle или WebView-хранилища. Регистрация публикуется только после надёжного сохранения `registered`. Ошибку сохранения нельзя выдать за успех; успешно сохранённая привязка с истёкшим до публикации JWT восстанавливается через `token`, а не новый `pair`.

Контракты `/auth/mobile/pair` и `/auth/mobile/token`, проверка QR, согласованности carId/userId/audience, срока по serverTime/exp/expiresIn и монотонным часам, запрет redirects, поправка timestamp только для следующей попытки и безопасные ошибки переносятся из iOS. Сервер проверяет подлинность QR JWT; клиент лишь разбирает структуру и контекст. URL из QR не становится адресом API или веба.

Новая установка/перенос не восстанавливают авторизацию. Помимо `allowBackup=false` задаются подходящие правила исключения cloud backup и device transfer; авторизационные файлы размещаются в no-backup storage. При обычном обновлении APK с тем же applicationId и ключом подписи привязка сохраняется.

Обычная отвязка закрывает документ и bridge, останавливает сессию, удаляет ключ/метаданные и проверяет удаление перед welcome. Статический веб-кеш сохраняется. Подтверждение из веба не повторяется в native; очистка принадлежит координатору и переживает отмену bridge-вызова при закрытии WebView.

## 6. Менеджер сессии и жизненный цикл

Сохраняются одна общая авторизационная операция, независимая отмена ожидающих потребителей, защита от поздних результатов старой привязки, публикация событий и истечение на монотонных часах. Валидный JWT остаётся доступным при неудачном обновлении; истёкший не возвращается. Повтор той же строки JWT не считается успешным refresh.

Упреждение refresh — 120 секунд; интервалы повторов рабочего режима 5/10/20/30/30 секунд с дальнейшим ограничением 30 секундами. Ошибка первоначального входа требует пользовательского повтора; рабочий режим после первого показа продолжает согласованные повторы. Истечение JWT само по себе не закрывает уже показанный живой веб.

В фоне новые плановые запросы не запускаются. Начатая операция может завершиться, пока процессу предоставляется время; периодическая работа в фоне не гарантируется. На foreground заново проверяются дедлайны, запускается необходимое получение JWT, уведомляется веб. Foreground Service, уведомление и WorkManager ради постоянного refresh не добавляются.

После смерти процесса используются только сохранённая привязка и новый `token`; DOM, позиция прокрутки и стек JS не гарантируются. Activity recreation не должна запускать параллельную регистрацию или применять старый результат; ViewModel сохраняет бизнесовую операцию в живом процессе. Реальное уничтожение WebView создаёт новый документ и требует новой готовности. Сам WebView не удерживается в application-singleton с Activity context.

## 7. Android WebView и bridge

Публичный JS-контракт сохраняет `getSession`, `recoverUnauthorized`, `getHostState`, `reportReady`, `unlinkCar`, формы ошибок и session/host событий. `unlinkCar` остаётся void с поглощением технического rejection. `platform=android`, appVersion, bridgeVersion и тема устройства передаются при запуске `/index.html`, с сохранением постороннего query и без дублей. Тема устройства light/dark и тема Stackflow android/cupertino — разные настройки.

Вместо WebKit message handler используется AndroidX WebKit: origin-scoped `addWebMessageListener` и внедрение bootstrap на старте документа. Поддержка `WEB_MESSAGE_LISTENER` и `DOCUMENT_START_SCRIPT` проверяется у установленного провайдера WebView; одного minSdk недостаточно. Если функций нет, приложение показывает понятную ошибку о необходимости обновить WebView, не выдавая JWT небезопасному fallback. Эти проверки и пользовательское ограничение согласованы; общая диагностика всех возможностей браузера не добавляется.

Android-транспорт сам связывает Promise с ответом через внутренний requestId; бизнесовые методы не получают новых аргументов. Проверяются фактический sourceOrigin, isMainFrame, текущий контейнер/документ и структура сообщения. Нельзя полагаться только на переданный из JS documentId или подставлять `*` в список разрешённых origins. Bootstrap внедряется только для доверенного origin, публичный API создаётся только в главном frame. Ответ/событие закрытого документа не применяется к новому.

Перед полной загрузкой полномочия старого документа прекращаются. Для Android отдельно подтверждается соответствие событий навигации и document-start bootstrap: порядок ранних вызовов, готовность/commit, redirect, замена, отмена и запоздалые callbacks. Успешный `onPageFinished` не является `reportReady`. Это обязательная ранняя техническая проверка, а не предположение о полном совпадении с WKNavigation.

Первый WebView готовится после первого нативного кадра и раскрывается только при действующем JWT и принятом `reportReady({screen: content|error})`. Бюджет готовности — 60 активных секунд после доступности JWT, фон его приостанавливает; редирект и refresh его не перезапускают. Предварительная загрузка не раскрывает веб на welcome.

Главный документ остаётся в доверенном origin; явные внешние HTTP(S)-ссылки открывает браузер, внешние автоматические переходы блокируются. Подресурсы CDN допускаются, iframe не получает JWT. HTTP 4xx/5xx главного документа, ошибки TLS/навигации и таймаут показывают нативную ошибку; ошибки отдельных ресурсов сами по себе не заменяют экран. TLS-ошибки никогда не обходятся через proceed. Полная browser-history навигация не подменяет Stackflow.

При смерти renderer Android запрещает повторно использовать пострадавший WebView: он уничтожается, отзываются его документ/bridge и создаётся новый экземпляр. Пользовательское поведение повторяет текущий iOS: после первого показа разрешена одна автоматическая попытка восстановления с сохранением привязки/менеджера и новым reportReady. До завершения этой попытки повторная смерть renderer показывает нативную ошибку без бесконечного цикла. Успешная готовность после восстановления снова разрешает автоматическую попытку при будущем сбое. До первого показа — ошибка с явным повтором. Статический профиль/кеш сохраняется; JS-состояние теряется.

## 8. Изменения общего веба

### Тема

В точке создания Stackflow тема выбирается из проверенного launch platform: Android → `android`, iOS → `cupertino`. Поведение обычного веб-запуска не меняется случайно из-за отсутствующего параметра: существующее значение остаётся fallback. Стопка, страницы и контроллер навигации переиспользуются. Системный Android Back запускает штатный переход после завершения жеста; интерактивный predictive progress не входит в согласованный вариант. Патч библиотеки и gesture exclusion не нужны.

### Команда Back

Расширяется существующее событие `zdeep:host-event`: `{type: 'back', sequence: number}`. Android bootstrap доставляет его только текущему доверенному главному документу. Публичный метод `window.ZdeepNative.back()` не требуется: направление команды native → web.

Парсер host events и HostLifecycleProvider дорабатываются совместно: Back нельзя случайно трактовать как refresh в нынешней ветке `else`. Sequence остаётся общим монотонным счётчиком текущего host, повторное/устаревшее событие игнорируется. Стандартные lifecycle/refresh события и getHostState не ломаются. Специальный request/response результат Back не нужен: native не выходит на корне даже при отсутствии обработчика.

Вебовый диспетчер Back предлагает команду одному верхнему модальному слою через существующее действие отмены/закрытия с его guards. Сейчас найдены два компонента: `UnlinkCarDialog` (также удаление аккаунта) и `SentryHelpSheet` (справка о Страже/Автостраже). У `UnlinkCarDialog` закрытие запрещено при `submitting`: Back поглощается без закрытия и без перехода на предыдущий экран. У `SentryHelpSheet` переиспользуется `requestClose`; пока слой ещё присутствует во время exit-анимации, следующий Back не должен пройти к стеку. Закрытие destructive confirmation не подтверждает действие. Если слоёв нет, вызывается существующая команда навигации из `NavigationRoot`, чтобы сохранить guards и запись в уже имеющуюся диагностику Sentry. Регистрация обработчиков следует фактическому присутствию модала, очищается при размонтировании и хранит лишь порядок и callback; новые идентификаторы слоёв, приоритеты и универсальная modal-система не нужны. Escape/backdrop и Android Back используют одно действие закрытия с прежними ограничениями. Проверяются вложенные слои и повторные команды во время анимации, чтобы один Back не закрывал модал и экран одновременно.

Android перехватывает системный Back только для основного показанного веб-сценария; на корне остаётся no-op по прямому решению пользователя. Home и переключатель приложений сохраняют системное поведение. До готовности документа команда не буферизуется для последующего неожиданного pop. iOS не начинает отправлять Back и сохраняет прежнюю навигацию.

## 11. Критерии готовности

1. Testing Debug APK собран и установлен в эмулятор; обе Debug-конфигурации используют правильные адреса. Production Release настроен для будущей сборки с внешней подписью, но не собирается в рамках задачи. Итоговый отчёт явно отделяет проверенные Debug-сборки от непроверенной release-сборки.
2. Welcome, справка, разрешение камеры, реальное сканирование QR-картинки в эмуляторе, одна регистрация и переход через иллюстрированную загрузку до живого веб-контента работают.
3. Local pair/token подтверждают совместимость P-256 SPKI и DER signature с настоящим backend; проверяются carId и пользовательские бизнесовые данные, а не только наличие HTML.
4. Холодный старт с привязкой получает JWT без QR; обновление APK с той же идентичностью сохраняет вход; удаление/новая установка требуют QR. Восстановление метаданных без ключа не публикует JWT.
5. Concurrent refresh/getSession/recoverUnauthorized, срок, backoff, поправка времени, отмена, ошибки хранения и сетевые ошибки покрыты значимыми тестами. Контекст после успешного сохранения registered не теряется из-за истечения JWT.
6. Background/foreground и смерть процесса не создают параллельный pair, не публикуют запоздалый JWT и не раскрывают веб без валидной сессии/готовности. Проверяются readiness timeout и повтор.
7. Bridge доступен на старте доверенного главного документа; iframe/чужой origin/старый документ не получают токен. Проверяются redirects, полная навигация, reload, ответы после отмены и renderer recovery.
8. Android Back работает с кнопками и жестовой системной навигацией: клавиатура → верхний модал → стек → no-op на корне. iOS-тема/свайп и существующие session/lifecycle/refresh контракты веба не регрессируют.
9. Отвязка из веба и подтверждаемая отвязка из нативной ошибки завершают очистку до welcome; повторные/устаревшие команды не запускают вторую очистку. Сбой очистки требует повтора, а не скрытого входа.
10. Вебовый Sentry остаётся работоспособным; токены, ключи, QR и подписи не попадают в артефакты/логи. Debug-панель, mailbox, нативный Sentry/Firebase отсутствуют по объёму задачи.
11. Репозитории содержат русскую инструкцию сборки, local-подготовки, установки APK и ручной testing-проверки с QR-картинкой. Код и конфигурация не содержат реальных QR/JWT или ключа подписи Release.

Автоматические сетевые проверки используют только local. Testing нужен для ручной проверки пользователя; её результат не объявляется выполненным заранее. Приёмка на эмуляторе явно не доказывает качество физической камеры, аппаратного Keystore и поведения OEM/реального устройства. Не подменять это обещанием «проверено на всех современных телефонах».

Проверить доступность local API/веба также из эмулятора; успех `curl localhost` на Mac не доказывает доступность `10.0.2.2` из Android. Инструменты не переустанавливаются целиком, если достаточно указать существующую JDK или доставить один нужный SDK image.

Основная среда разработки и проверок — обычный телефонный AVD Android 16 / API 36. На нём выполняются Android unit, component и platform/localbackend наборы, а также QR-проверка через Virtual Scene camera. `minSdk = 30` сохраняет установку на Android 11+, но API 30 не входит в обязательную матрицу исполнения этой задачи. Записываются фактические API, ABI, версия WebView-провайдера и результаты двух feature checks. Полная матрица производителей и планшетов не нужна.

Следующие ранние проверки, до основной UI-работы: настоящий Keystore + local pair/token; bridge на старте документа и после reload; готовая камера с QR-картинкой; доступная Android-тема Stackflow и Back; пересоздание WebView после renderer loss. Если проверка не проходит, сначала исправляется узкая интеграция, а не пишется остальное приложение в расчёте, что она заработает позже. Проверочные прототипы не считаются завершёнными пользовательскими сценариями.

## 13. Система unit- и интеграционных тестов

### 13.1. Уровни и границы подмены

Технический выбор исполнителя для планирования: JUnit4, `kotlinx-coroutines-test`, AndroidX Test / AndroidJUnitRunner и MockWebServer той же совместимой линии OkHttp. Для нативного UI использовать официальный Compose Test API совместимой стабильной версии; для системных разрешений и Back — UI Automator там, где Compose не имеет доступа. Не вводить одновременно JUnit5, Robolectric, отдельный mocking framework, собственный test runner и несколько способов управления эмулятором без конкретной потребности. Веб использует уже настроенные Vitest / Testing Library и Playwright.

| Набор | Место | Что настоящее | Что можно подменить | Внешние зависимости |
| --- | --- | --- | --- | --- |
| Unit | Android `app/src/test/.../unit` | Проверяемая бизнес-логика, парсеры, политика времени, состояния | HTTP, часы, storage на границах | Нет backend, WebView и эмулятора |
| Component integration | Android `app/src/test/.../component` | Несколько бизнес-компонентов вместе; отдельно настоящий OkHttp с MockWebServer | Ответ сервера и управляемые сбои storage; Android Keystore/WebView здесь не используются | Только локальный fixture-сервер текущего теста |
| Android integration | Android `app/src/androidTest/java/ru/zdeep/mobile/tests/platform` | Настоящие Keystore, AtomicFile, WebView, bridge bootstrap, Activity/Compose, системный Back | Авторизационные ответы для изолированных сценариев; HTTP(S) fixture-документы | Эмулятор; настоящий backend не нужен |
| Local end-to-end | Android `app/src/androidTestLocalDebug/java/ru/zdeep/mobile/tests/localbackend` и небольшой host-сценарий для перезапуска процесса | Local API, настоящий общий веб, Keystore, транспорт, WebView, сценарий входа | Нельзя подменять auth/bridge для доказательства сквозного входа | Запущенные local API/веб и эмулятор |
| Web regression | Существующие web unit/integration suites | Host parser/provider, диспетчер Back, реальные Stackflow-команды и компоненты модалов | Native host-событие можно подать из теста | Существующая инфраструктура веб-репозитория |

«Unit» и «component» находятся в стандартном JVM source set. Platform instrumentation находится в общем `androidTest` source set, а localbackend instrumentation — в `androidTestLocalDebug`, чтобы локальная сквозная проверка не попадала в Testing-вариант. Для разделения не нужны дополнительные Gradle-модули или новые product flavors. Чистая бизнес-логика не должна зависеть от `android.*`; Android-зависимые проверки выполняются на устройстве, а не «проходят» с `returnDefaultValues=true`.

### 13.2. Минимальные фикстуры и контролируемое время

Переиспользовать подход из `ZDEEPTests/Support/LocalAuthFixture.swift`: маленькие fakes для auth/storage, счётчики вызовов и управляемая точка завершения. На Kotlin использовать `CompletableDeferred` или эквивалент для паузы ответа/сохранения; `runTest` и общий `TestCoroutineScheduler` — для coroutine-задач и таймеров. Передавать dispatcher/clock только компонентам, которым это нужно; не создавать общий контейнер зависимостей для тестов.

Монотонное время и wall time проверяются отдельно: сдвиг wall time не продлевает срок JWT; продвижение виртуального времени запускает нужный refresh. Clock, который отдаёт now, и scheduler задержек обязаны смотреть на одно виртуальное время. `advanceTimeBy` с явным выполнением задач на границе используется там, где важен точный дедлайн. Не использовать `Thread.sleep`, реальные минуты ожидания и безусловный `advanceUntilIdle` для бесконечно возобновляемого refresh. Сетевые и WebView-тесты ждут наблюдаемого события с конечным общим timeout; виртуальные часы не объявляются способом управлять сетью или renderer.

Нужные fakes/fixtures: управляемый auth-транспорт или auth client; storage с ошибкой на нужной операции; тестовые часы; HTML для раннего bridge/iframe/навигации; MockWebServer responses для redirects, chunks и не-JSON ошибок. Использовать готовый MockWebServer вместо написания своего HTTP-сервера по образцу Swift NWListener. Синтетические QR/JWT в фикстурах допустимы и помечены как синтетические; настоящие токены не встраиваются в исходники или golden-файлы.

На Unit/Component каждый сценарий получает новые экземпляры manager/fakes. Android storage-тесты используют отдельные app-owned aliases и временные файлы; teardown удаляет только созданные тестом объекты. Тесты Keystore/storage не очищают весь пользовательский профиль приложения. Сценарии, требующие чистой установки, запускаются отдельно и последовательно на выделенном local AVD. Параллельные тесты не делят одну привязку, а fixture-серверы используют свободный порт и закрываются после теста.

### 13.3. Проверки Android, которые нельзя заменить JVM-тестами

- Keystore: генерировать P-256, извлекать SPKI, подписывать и проверять DER-подпись публичным ключом; восстанавливать metadata новым экземпляром BindingStore; проверять потерянный ключ и удаление. Unit fake ключа не доказывает Android Keystore.
- Bridge: загружать HTML по HTTP(S) с контролируемого fixture-origin, включённого в конфигурацию тестового WebSession. Не использовать `file://`/`data:` как доказательство origin-проверок и не ослаблять production allowlist до `*`. Первый inline-script реально вызывает `getHostState`/`getSession`; проверяются main-frame и iframe, отказ чужому origin, reload и поздний ответ старому документу.
- WebView: все UI-вызовы на main thread; wait на тестовом потоке. Учитывать, что Compose idle не означает готовность страницы/сетевого запроса. Ждать существующий reportReady/изменение состояния, а не фиксированный sleep; технический JS-хелпер остаётся внутри androidTest, без runtime mailbox.
- Renderer loss: использовать поддерживаемый платформенный способ завершения renderer (например `WebViewRenderProcess.terminate()` после появления renderer handle), дождаться настоящего callback и проверить освобождение старого экземпляра. Fakes остаются для unit-политики. Отсутствующий renderer handle — невыполненная предпосылка обязательного теста, а не успешный no-op.
- Activity recreation: настоящий `ActivityScenario.recreate()`, сохранение одной бизнесовой операции и новая готовность при новом документе. Process death: отдельная host-команда adb после завершения фазы подготовки, повторный старт и проверка нового процесса; нельзя убить instrumentation в его процессе и выдать оборванный отчёт за успех.
- Back: вебовый тест событий проверяет алгоритм, Android-тест проверяет доставку реальной системной команды. Нужны клавиатура, обычный стек, корень, запрещённый к закрытию диалог и закрывающаяся шторка. Кнопочная и жестовая навигация проверяются на выбранном AVD; браузерный `history.back()` не считается эквивалентом.

### 13.4. Сквозной local-сценарий и камера

Перед local end-to-end проверяются прямые HTTP 200 без redirects от API `/health` и настроенного web URL с Mac и доступность из эмулятора. Недоступность — ошибка подготовки с ненулевым результатом, а не `Assume`, `@Ignore` или переход на testing. Unit/Component/Android platform не должны требовать работающий backend.

Минимальный настоящий сетевой сценарий: получить свежий local carToken существующим endpoint → pair с Keystore-подписью → сохранить registered → открыть настоящий веб и дождаться reportReady и признака бизнес-контента → закрыть/восстановить приложение без QR через token → отвязать локальную привязку → welcome. Проверять согласованность carId и наличие авторизованных бизнесовых данных; HTML 200 и наличие JS-объекта недостаточны. `/token` отдельно вызывается явно в локальной интеграции, без реального ожидания истечения JWT; время/backoff покрываются детерминированными тестами.

Backend-интеграция может подавать результат разбора QR через test-only подготовку для изоляции auth; это не считается проверкой камеры. Отдельный обязательный сценарий получает свежий local QR, помещает его изображение в Virtual Scene camera, открывает штатный сканер и проходит вход. Файл QR — временный вне git, удаляется после сценария; QR и токен не включаются в обычные отчёты/скриншоты. Если автоматическая настройка Virtual Scene для выбранного AVD не воспроизводится, исполнитель фиксирует ручную подготовку и отдельный подтверждённый прогон; fake-кадр не заменяет этот критерий. Testing QR пользователя используется только им для ручной приёмки.

Никаких product-параметров «пропустить авторизацию», «вставить JWT», «открыть debug панель» для тестов. Зависимости/хелперы находятся в test/androidTest; test host Activity и fixture allowlist не попадают в production manifest/APK. Реальные local данные для destructive web-действий должны быть специально созданы тестом; не удалять аккаунт/машину пользователя ради покрытия.

### 13.5. Выборочный запуск, итоговый запуск и отчёты

План фиксирует реальные package names и точные команды после создания проекта. Ожидаемые стандартные точки входа: `:app:testLocalDebugUnitTest` для Unit+Component и `:app:connectedLocalDebugAndroidTest` для инструментальных проверок. Отбор JVM — стандартный `--tests`, Android — `android.testInstrumentationRunnerArguments.class/package/notPackage`. Без селектора instrumentation выполняет и localbackend, поэтому для platform-only нужна явная фильтрация. Команды в README должны работать дословно; название ещё не созданной Gradle-задачи не считается проверенной командой.

Для каждого прогона указываются checkout/revision, variant, JDK, serial/API AVD, команда, выполненные классы/тесты, итог и пути к JUnit XML/HTML/инструментальным отчётам. Нулевое число выбранных тестов, skipped обязательного сценария, завершение runner до результатов или только `UP-TO-DATE` без ссылки на соответствующий прошлый прогон не подтверждают новый успех. Обычный повтор с неизменившимся кодом может использовать Gradle cache; финальный прогон должен иметь подтверждённое исполнение обязательных наборов. Отчёт не содержит реальных JWT, подписей, QR и приватных ключей.

Во время реализации запускается затронутый лёгкий набор; сложный integration запускается при изменении соответствующей границы. После готовности один полный local прогон на Android 16 / API 36 AVD и web regression для изменений общего веба. Не запускать весь набор после каждого изменения и не скрывать flaky-тест повтором до зелёного. Первый сбой сохраняется с причиной; исправление подтверждается новым результатом. Android-тесты не должны требовать Xcode/iOS Simulator; сценарии iOS служат образцами, проверка общего веба обеспечивает отсутствие регрессии Android/iOS веток.

Для productionRelease в этой задаче проводится только проверка исходной конфигурации: адреса, release-настройки, отсутствие test/debug-зависимостей и entry points, настройка будущей внешней подписи. Release APK не собирается; его merged manifest/APK, minification на готовом артефакте и фактическая подпись здесь не проверяются. Это явно указывается в поставке. Не запускать сетевые тесты против production. Сборка unsigned Release также не нужна.

### 13.6. Когда система тестов готова

Система готова, когда: каждый ID из §12.4 связан с конкретными тестами и результатом; отдельно воспроизводятся JVM, Android platform и local end-to-end; platform работает без backend; отсутствие backend явно ломает local preflight; настоящий bridge/Keystore и камера проверены на AVD; смерть процесса не заменена recreation; ошибку и пропуск нельзя выдать за успешную приёмку. Процент coverage и число тестов не являются целью, механический перенос всех iOS-тестов не требуется.

До реализации документ проверяется пользователем или выбранным им сильным ревьюером; затем составляется план на английском. В реализации native-код по правилам проекта поручается Luna High, обычное ревью — Terra medium; после завершения плана более чем из трёх задач — Sol high review. GitHub-операции не выполняются.
