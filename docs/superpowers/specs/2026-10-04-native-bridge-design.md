# ZDEEP iOS: нативный bridge

Дата: 2026-10-04.

Статус: решения согласованы в отдельном brainstorming; письменная спецификация ожидает проверки пользователя. Реализация не начата.

Связанные документы: [общая архитектура](2026-10-03-mobile-session-design.md), [контейнер WebView](2026-10-04-webview-container-design.md), [менеджер сессии](2026-10-03-session-manager-design.md), [веб-контракт и доработки](2026-10-03-webview-bridge-prerequisites.md).

## 1. Ответственность

Bridge адаптирует менеджер сессии и состояние host к JavaScript текущего документа. Он проверяет источник вызова и параметры, обслуживает четыре метода, доставляет события и передаёт готовность координатору. JWT и его планировщик принадлежат менеджеру; навигация принадлежит контейнеру; показ и удаление привязки — координатору.

Бизнесовый bridge доступен в Debug и Release. USB mailbox и диагностическое выполнение JavaScript остаются отдельными механизмами, их готовность не открывает продуктовый экран.

## 2. Транспорт

Используем штатный `WKScriptMessageHandlerWithReply`, без дополнительной библиотеки. Альтернатива с собственным реестром JS-callback и ручной доставкой каждого ответа не выбрана.

До выполнения скриптов приложения на старте главного документа в `.page` внедряется `window.ZdeepNative` с четырьмя методами. Методы отправляют сообщения обработчику WebKit и возвращают Promise. Наличие API не предоставляет полномочия: обработчик проверяет главный frame, точный доверенный origin, текущие документ и привязку.

Вызов содержит метод, его параметры и внутреннюю транспортную идентичность документа. Документная идентичность не является ревизией JWT или версией bridge. При начале полной навигации прежние полномочия прекращаются до доставки поздних ответов. До commit прежний документ может оставаться в памяти WebKit, но больше не обслуживается. Новый документ получает новый транспортный контекст; навигационная попытка и документ проверяются совместно. Полный back/forward контейнер блокирует, отозванный транспорт не оживает через историю.

Ответы сериализуются структурированно. Ошибка WebKit передаётся строкой; для сохранения `AuthError` нативный адаптер и внедрённая JS-обёртка используют ответ с результатом или структурированной ошибкой. Обёртка возвращает согласованное значение либо отклоняет Promise объектом ошибки. Сырой ответ HTTP и секреты в ошибки не включаются.

Обработчик завершает каждый принятый вызов не более одного раза. При закрытии документа его ожидания завершаются отменой; ответ старого вызова не направляется в новый документ. Отмена потребителя отсоединяет его от общего обмена JWT, но не отменяет общий запрос менеджера.

### 2.1. Привязка документа к навигации

Контейнер — единственный владелец актуальности документа. Он хранит один контекст текущей подготовки/документа: случайный `documentId`, идентичность навигационной попытки, её `WKNavigation` после появления и состояние `preparing`, `committed` или `closed`. Bridge использует этот контекст и хранит только ожидающие ответы; отдельный реестр поколений или второй источник актуальности не создаётся.

1. Перед собственным `load`/reload либо разрешением новой полной навигации главного frame контейнер создаёт контекст и отзывает прежний. Для собственной загрузки первый policy callback использует уже подготовленный контекст, а не создаёт второй.
2. До запуска/разрешения навигации контейнер устанавливает bootstrap `WKUserScript` с этим `documentId`, `.atDocumentStart`, `.page`, только главный frame. ID захватывается JS-обёрткой в замыкании. Перестройка набора скриптов сохраняет необходимые инфраструктурные скрипты; пустой прежний bootstrap заменяется. Уже работающий старый документ не получает новый ID.
3. `didStartProvisionalNavigation` связывает полученный `WKNavigation` с подготовленной попыткой через существующий `NavigationCallbackGate`. Разрешённые серверные редиректы внутри этой попытки сохраняют ID и бюджет; смена конечного URL сама по себе не создаёт новый документный контекст. Переход SPA, запрещённый back/forward и внешняя ссылка контекст не заменяют.
4. Сообщение принимается только с ID этой попытки, главным frame доверенного origin и актуальным контейнером. До актуального `didCommit` правильный вызов удерживается вместе с его reply handler, без выдачи сессии и выполнения бизнесового метода. Чужой/отозванный ID отклоняется сразу.
5. Актуальный `didCommit` переводит контекст в `committed`, после чего удержанные вызовы исполняются по обычным правилам методов. Сохраняется порядок начала обработки, но ответы завершаются независимо: не ждём завершения одного асинхронного метода перед запуском следующего. Ожидающий JWT `getSession` не блокирует `getHostState` или `reportReady`; общий запрос авторизации по-прежнему объединяет менеджер. `getHostState` после commit не ждёт авторизацию, ранний `getSession` продолжает ждать первый JWT.
6. Ошибка, остановка или замена подготовки закрывает её контекст и завершает удержанные и выполняющиеся ожидания отменой. Поздний `didCommit` не открывает его снова.

У вызовов до commit нет отдельного нового таймера: они подчиняются попытке загрузки и её бюджету из спецификации координатора. Это внутренняя привязка транспорта; дополнительного метода handshake в `window.ZdeepNative` нет.

### 2.2. Формат сообщения и исхода

Один обработчик принимает фиксированный набор четырёх методов. Внутренний запрос:

```ts
{ documentId: string, method: 'getSession' | 'recoverUnauthorized' |
  'getHostState' | 'reportReady', params: null | { screen: 'content' | 'error' } }
```

Для первых трёх методов `params` равен `null`, для `reportReady` — объект с единственным полем `screen`. Некорректный метод/параметры завершают вызов безопасной локальной ошибкой. Идентификатор запроса в JS не нужен: ответ связывает `WKScriptMessageHandlerWithReply`.

Нативный ответ имеет ровно один из видов:

```ts
{ ok: true, value: unknown } // reportReady: value = null
{ ok: false, error: AuthError }
{ ok: false, cancelled: true }
```

JS-обёртка возвращает `value` (для `reportReady` — `undefined`), отклоняет Promise объектом `AuthError` либо стандартным `AbortError` для отменённого документа. Ответ метода `recoverUnauthorized` с `unavailable`/`terminal` является успешной доставкой его результата, а не транспортной ошибкой. Изначальный отказ WebKit также отклоняет Promise; его строка не подставляется как пользовательское серверное объяснение.

| Ситуация | Публичный исход |
| --- | --- |
| Первоначальный вход ещё не завершился | `getSession` ожидает публикацию; отдельный HTTP-запрос не начинает |
| Ошибка текущего первоначального входа | `getSession` отклоняется с `AuthError` текущей попытки |
| Ранее опубликованный JWT истёк, нового нет | `getSession` отклоняется с последней ошибкой либо локальным `AuthError` о временной недоступности |
| Нет первой сессии | `recoverUnauthorized` возвращает `unavailable` с `reason: temporary` |
| Обновление не удалось | `recoverUnauthorized`: `unavailable`, `reason: expired` при отсутствии действующего JWT, иначе `temporary`; ошибка при наличии |
| Повреждённый контекст/запрещённая идентичность | `recoverUnauthorized`: существующий `terminal`; `getSession` отклоняется с локальным `AuthError` |
| Отозван/закрыт документ | Отмена всех его методов с `AbortError`, без нового экранного перехода |
| Готовность ещё не допустима либо ожидание завершено | `reportReady` отклоняется с безопасным локальным `AuthError` |

Для событий контейнер и bridge также проверяют ID до отправки, а JS-приёмник проверяет захваченный ID перед `dispatchEvent`. Это защищает от выполнения уже отправленного JS в сменившемся документе. Значения передаются аргументами фиксированного JS-вызова; общий RPC-диспетчер и дополнительные публичные методы не требуются.

## 3. Методы

| Метод | Поведение |
| --- | --- |
| `getHostState()` | Немедленно вернуть актуальные `appState` и lifecycle `sequence`, независимо от авторизации |
| `getSession()` | Вернуть действующий JWT из менеджера либо дождаться текущего первоначального входа; сам вход не запускать |
| `recoverUnauthorized()` | После первой сессии выполнить или присоединиться к одной общей попытке обновления; до первой сессии вернуть `unavailable` |
| `reportReady({ screen })` | Проверить источник и передать `content` либо `error` координатору для принятия готовности |

Несколько первоначальных `getSession()` ждут общую публикацию. Ошибка текущего входа завершает эти ожидания с `AuthError`; отмена или смена документа — с отменой. До JWT отдельного таймаута чтения нет. Запрос авторизации ограничен 30 секундами, а первое ожидание готовности начинается только после доступности JWT и ограничено 60 активными секундами.

Действующий JWT возвращается сразу, даже во время обновления или после неудачной попытки обновления. После истечения ранее опубликованного JWT `getSession()` отклоняется с временной ошибкой; подписка продолжает работать.

`recoverUnauthorized()` не возвращает старый JWT как результат успешного обновления. Если HTTP 200 содержит ту же строку последнего опубликованного JWT, менеджер возвращает ошибку обновления; bridge преобразует её в `unavailable`. Событие смены сессии не отправляется, повторы режима работы продолжаются с текущим счётчиком. Он ждёт одну попытку, а не всю серию повторов. Успех возвращает `ready` с опубликованной сессией, неуспех — `unavailable` с причиной и безопасной ошибкой. `terminal` сохраняется для повреждённого контекста либо запрещённой смены идентичности, без автоматического удаления ключа. Сетевые ошибки и истечение сами по себе не терминальны.

Публичный TypeScript-контракт, структуры `AuthError` и `SessionRecovery` описаны в связанном веб-задании. Внешних полей `revision` и `protocolVersion` нет.

## 4. Срок JWT

Native — единственный источник решения о действительности JWT. Менеджер рассчитывает срок по серверному времени и монотонному дедлайну. Перед ответом или доставкой `sessionChanged` проверяется, что токен ещё действует и не заменён.

Веб проверяет структуру сессии и неизменность `carId`/`userId`, но не сравнивает срок с `Date.now()` и не создаёт второй таймер истечения. `expiresAt` остаётся UTC ISO 8601 информационным полем. Смещение часов и оставшийся срок в контракт не добавляются.

Использование токена прекращается по `sessionExpired` либо результату восстановления после HTTP 401. После foreground веб сверяется через `getSession()`; до успешной сверки возобновление запросов контролируется существующим веб-провайдером.

## 5. Принятие готовности

Для первого открытия, явного повтора авторизации с новой загрузкой документа, каждой разрешённой полной навигации после показа и восстановления веб-процесса координатор создаёт отдельное ожидание текущей попытки и нового документа по спецификации контейнера. Режим работы менеджера при новой навигации сохраняется.

Координатор принимает готовность только при действующем JWT, актуальных привязке и документе и продолжающемся ожидании этого документа. Оба `screen` — `content` и `error` — допустимы. HTML, диагностическая готовность и получение JWT не заменяют сигнал.

До действующей сессии вызов отклоняется. После отмены, таймаута или замены документа он также отклоняется и не открывает экран. При успешном принятии координатор сохраняет факт готовности; повтор того же принятого документа успешно подтверждается без нового перехода, пока документ актуален.

Успешно принятое `reportReady` завершает отсчёт готовности и отменяет его таймер. Ожидание активности либо нового действующего JWT до фактического показа больше не расходует этот бюджет. Если документ меняется или пользователь начинает новый сценарий, требуется новая готовность и новый бюджет.

В фоне принятую готовность сохраняем. Успешный ответ означает принятие, а не фактическую видимость. При возвращении координатор проверяет актуальность и действующий JWT перед показом; без JWT показ откладывается. После отмены или таймаута сохранённая готовность не оживляет завершённое ожидание.

Веб отмечает готовность отправленной после успешного подтверждения и разрешает повтор при отказе, прекращая повторы при завершении документа. Частоту и механизм повторов веб определяет в своей доработке; нативный бюджет готовности остаётся единственным таймаутом первого показа.

## 6. События native → веб

| Событие | Условие |
| --- | --- |
| `zdeep:session-event`, `sessionChanged` | Каждая актуальная публикация JWT; содержит полный `accessToken`, `carId`, `expiresAt` |
| `zdeep:session-event`, `sessionExpired` | Один раз для истёкшей последней сессии; последняя ошибка обновления передаётся при наличии |
| `zdeep:host-event`, `lifecycle`/`refresh` | Существующий host-контракт с `sequence` сохраняется |

События доставляются текущему доверенному главному документу. Очереди для будущего документа нет: если JS ещё не готов или документ заменён, состояние восстанавливается через чтение. Веб ставит подписку перед первоначальным `getSession()` и не применяет поздний ответ поверх более нового события.

Публикации и доставка упорядочены. Непосредственно перед выполнением JS проверяются актуальность документа, привязки и события. Запоздалое истечение старого JWT не сообщает потерю уже обновлённой сессии. Значения передаются как данные, без подстановки токенов в исполняемый JS-текст.

Неуспех отправки события не вызывает перезагрузку, сброс ключа или ошибку поверх работающего WebView. После foreground чтение восстанавливает актуальное состояние.

## 7. Остановка и диагностика

При закрытии или замене документа прекращаются приём вызовов, события и подписки этого документа; ожидающие потребители отсоединяются. Новый документ подключается к прежнему менеджеру сессии. Отмена входа или подтверждённый сброс отдельно останавливают менеджер и удаляют привязку через координатор, закрывают старый контейнер и создают новый WebView с тем же постоянным хранилищем. Старая история не переносится; ссылки на старый bridge и WebView освобождаются.

Диагностика может содержать метод, идентичность попытки, факт результата и безопасную категорию ошибки. JWT, QR-токен, ключи, подписи и полные тела ответов не записываются. Ошибка метода не становится нативным экранным переходом без решения координатора.

## 8. Приёмка будущей реализации

1. Четыре метода доступны до выполнения веб-приложения в Debug и Release.
2. Чужой origin, iframe и старый документ не получают нативную сессию.
3. Несколько ранних чтений ждут одну публикацию; ошибка входа завершает ожидания.
4. `getHostState()` не ждёт JWT; ранний `recoverUnauthorized()` не создаёт авторизацию.
5. Истёкший JWT не выдаётся; неверные часы устройства не заставляют веб отвергать действующую сессию.
6. Ошибка содержит поля `AuthError`; восстановление ждёт одну попытку, сохраняя периодические повторы менеджера.
7. Повтор принятой готовности идемпотентен; ранний, отменённый и запоздалый сигналы не открывают экран.
8. Готовность в фоне подтверждается, показ ожидает активность и действующую сессию.
9. Старое событие и поздний ответ не изменяют новый документ или новую сессию.
10. Закрытие документа отсоединяет его ожидания, сохраняя общий обмен JWT.
11. Пропущенное событие восстанавливается чтением на foreground; очереди для будущего документа нет.
12. Диагностика не содержит секреты; USB handshake не считается продуктовой готовностью.
13. Готовность нового документа после полной навигации принимается в новом ожидании; старая готовность не раскрывает его.
14. Неудача provisional navigation не возвращает старому документу полномочия bridge; сброс не оставляет доступный через историю старый контейнер.

Это требования к будущим проверкам, а не отчёт о выполненной реализации.

## 9. Основания

Веб-реализация просмотрена в локальном `zdeep-webview2` до коммита `7d81c59`. Основной контракт уже реализован; удаление проверок срока по часам устройства и подтверждаемый повтор `reportReady` пользователь выполняет отдельно. Тесты веба и совместная доставка с iOS в рамках этого проектирования не запускались.
