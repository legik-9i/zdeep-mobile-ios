# Завершение native Android-порта

Статус: проект дополнения для подтверждения пользователем. Основание: аудит `docs/verification/2026-11-02-android-result-audit.md` и согласованный порядок 2026-11-02. Дополняет исходную Android-спеку, не начинает новый порт.

## Результат и границы

Результат — работающий native Android-контейнер с поведением iOS в согласованной области, воспроизводимыми проверками и свежим Testing Debug APK. Разработка и приёмка: Android 16/API 36, minSdk 30. Проверка на физическом телефоне не требуется.

Общий веб-репозиторий не меняется. Back внутри сайта/модалов и Android-тема Stackflow полностью исключены из критериев этой задачи и реализуются отдельно. Production Release/R8/подпись/публикация и пользовательский testing-login отложены по решению пользователя; проверяется исходная production-конфигурация.

Уточнение пользователя 2026-11-02: разрешены изменения всего нативного Android-приложения, включая Kotlin-каталог `app/src/main/java/ru/zdeep/mobile/web/` с контейнером WebView, bridge и navigation. Запрет относится к отдельному репозиторию `/Users/oleg/projects/zdeep-webview2`. Прежняя запись о запрете Android `web/**` была ошибочной интерпретацией агента, не ограничением пользователя.

## Рассмотренные подходы

1. Только исправить функциональные дефекты: меньше правок, но прежний медленный цикл проверок сохраняется.
2. Узко исправить функционал, убрать доказанно лишнее и наладить тестовый цикл: выбран пользователем. Первым этапом обязательно упрощение проверок.

Новая архитектура, новые тестовые фреймворки, перенос всех Android-тестов на JVM и общий рефакторинг не нужны.

## Этап 1. Проверки прежде runtime-исправлений

Использовать Gradle/существующие scripts; новые команды — тонкие точки входа, без нового runner/framework:

- быстрые JVM: общий набор один раз, без настоящего 30-секундного HTTP timeout; конфигурационные assertions local/QA выполняются для обоих вариантов;
- HTTP integration: реальные подписи/транспорт, отмена, redirects и настоящий total deadline; медленный сценарий сохраняется, но не повторяется в каждом быстром проходе;
- выбранные Android-тесты: явный package/class/method selector, выбранный по изменённой границе;
- полная native-приёмка: необходимые JVM/HTTP checks, platform и локальный ordered driver, без общей веб-регрессии.

Точные команды и selectors фиксирует английский implementation plan после подтверждения этой спеки. Каждая команда должна запускать ненулевое число выбранных тестов и возвращать ошибку при failure/неожиданном skip; известный TLS ignore временно явно обозначается, не считается PASS.

Удалить точный дубль policy assertion. Исправить redirect-тест: дождаться наблюдаемого перехода/решения, а не проверять старый URL сразу после load. Keyboard/IME проверку привязать к реальному MainActivity/AppRoot; проверка host event не обещает работу Stackflow. Recreation smoke удалять только если более содержательные сценарии доказывают те же гарантии.

Сократить установки app/test APK внутри driver, сохранив намеренные install-over, смену окружения, uninstall/reinstall и разделение instrumentation при проверке смерти процесса. Не удалять защиту выделенного AVD, cleanup, проверку test discovery и секретность токенов.

Создать короткий русский skill внутри Android-репозитория `.codex/skills/android-testing/SKILL.md`: изменение → минимальный набор проверок, подготовка API36 AVD с host GPU/локальных сервисов, команды, критерии результата, поводы для расширения. Нет безусловного запуска полной приёмки после каждой правки. Измерить фактическое время команд; конкретный выигрыш заранее не обещать.

## Этап 2. Native-поведение

- Доставлять readiness timeout на main thread до чтения/изменения ViewModel. Проверить конфликт timeout с готовностью/cleanup; поздний timeout не возвращает ERROR после принятой готовности или очистки.
- Передавать light/dark из темы устройства при формировании launch URL. Смена темы обновляет значение следующей загрузки, не вызывает принудительный reload уже готового сайта; проверить начальный запуск и последующую загрузку.
- Проверить недоступность камеры при выданном разрешении; при подтверждённом пробеле показать понятную ошибку с доступным выходом, освободив ресурсы.
- Проверить настоящее открытие новой вкладки/окна бизнес-WebView по пользовательскому действию, затем исправить только подтверждённый пробел.
- Закрыть native TLS PREPARING ambiguity явным поведением и проверкой. Нельзя делать proceed/trust-all. Если Android callback не различает frames, использовать явно описанную безопасную политику отмены TLS/ошибки документа; не требовать невозможной точности iOS и не скрывать ограничение за Ignore.

Камера и новые окна — проверяемые риски, не заранее объявленные воспроизведённые баги. Не расширять реализацию, если проверка подтверждает корректность.

## Этап 3. Узкая чистка runtime

Удалить неиспользуемые WebSession параметры и недостижимые boolean-ветки после проверки всех callers. Оставить строгий runtime вход событий с явными request/session IDs; тестовые сокращения перенести в fixtures. Обеспечить понятное владение scheduler без утечки executor при уничтожении ViewModel. Сохранить монотонные дедлайны, cancellation и auth/storage гарантии. Публичный JS bridge-контракт не менять.

## Этап 4. Поставка и остановка

После этапов 1–3 выполнить финальный обзор изменений и одну полную native-приёмку на подготовленном API36 AVD. Исправления подтверждённых failures проверять сначала узкими selectors; полный повтор нужен только если изменения затрагивают уже принятые сквозные сценарии. Новый общий аудит без конкретной причины не запускается.

Поставка: свежий Testing Debug APK, SHA-256/версия/путь, установка и native launch на AVD; README с точными rebuild/install/test командами и краткий актуальный ledger. Android-документы становятся единственным актуальным источником статуса; iOS-копии помечаются как исходные/ссылки, без дальнейшего параллельного ведения.

Готово, когда этапы выполнены, найденные native-дефекты закрыты либо риск проверкой опровергнут, обязательные native-сценарии имеют зелёные доказательства на финальном коде, нет скрытых обязательных skips, артефакт совпадает с проверенной сборкой. Отдельные веб-задачи и ранее отложенный Release не препятствуют завершению этой цели.
