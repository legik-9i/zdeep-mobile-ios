# ZDEEP iOS: хранилище привязки

Дата: 2026-10-03.

Статус: спецификация по результатам отдельного brainstorming компонента. Решения согласованы в разговоре; письменный документ ожидает проверки пользователя. Реализация и её план пока не начаты.

Связанный документ: [общая спецификация приложения](2026-10-03-mobile-session-design.md). Здесь уточняются хранение привязки, восстановление и контракт работы с ключом.

## 1. Назначение и границы

Хранилище управляет одной локальной привязкой приложения к автомобилю: создаёт ключи, сохраняет состояние регистрации, подписывает переданные байты и выполняет очистку. Приватный ключ остаётся внутри компонента. Наружу передаются публичный ключ, идентификатор привязки, подтверждённый `carId` и результат подписи.

Клиент авторизации формирует тело HTTP-запроса и подписываемые байты, получает и проверяет ответ сервера. Менеджер сессии хранит JWT в памяти. Координатор показывает экраны, подтверждение сброса и выполняет переходы. Хранилище сообщает результаты и ошибки этим компонентам.

Зависимости: Keychain, криптографический API и небольшой локальный признак установки. Адреса сервера, настройки окружений и WebView компоненту не нужны.

## 2. Выбранный подход

Согласовано:

- создание ключей и подпись находятся в хранилище;
- ключи, состояние и `carId` сохраняются одной записью в Keychain;
- завершение регистрации определяется состоянием `registered`, отдельного флага авторизации нет;
- после переустановки прежняя привязка очищается;
- ошибки чтения и некорректные данные приводят к общему экрану ошибки с повтором либо подтверждённым сбросом.

Рассмотрены варианты: отдельный криптографический компонент и хранение метаданных вне Keychain. Выбранный подход уменьшает число компонентов и исключает необходимость согласовывать запись ключа и метаданных в двух хранилищах. Признак установки хранится отдельно, поскольку должен исчезать при удалении приложения.

## 3. Запись привязки

В Keychain хранится один сериализованный объект:

| Поле | Правило |
| --- | --- |
| `bindingId` | Новый случайный идентификатор при создании ключей; сохраняется на протяжении жизни этой привязки |
| Приватный ключ | Сериализованный ключ P-256; доступен только внутренним операциям хранилища |
| `publicCertificate` | Публичный ключ в формате DER/SPKI, Base64, который принимает сервер |
| `state` | Только `pending`, `registered` или `resetting` |
| `carId` | Отсутствует в `pending`, обязателен и непуст в `registered`; при переходе в `resetting` может сохраняться до удаления |

Отсутствие записи — отсутствие привязки, отдельное значение `state` для этого не добавляется. JWT, QR-токен и подписи отдельных запросов в запись не сохраняются. `bindingId` не является ревизией сессии, не меняется при обновлении JWT и не передаётся в бизнесовый bridge.

При чтении проверяются структура записи, допустимое состояние, обязательные поля, возможность восстановить приватный ключ и соответствие ему публичного ключа. Некорректная запись сообщает ошибку; обычное чтение автоматически её не удаляет.

Техническая основа из общей спецификации: CryptoKit для P-256 и небольшой адаптер Security для хранения сериализованных данных. Запись имеет доступность `AfterFirstUnlockThisDeviceOnly`, без синхронизации iCloud и обязательного биометрического диалога. Перенос привязки на другое устройство в эту версию не входит. Совместимость DER/SPKI и подписи подтверждается будущей интеграцией с бэкендом.

## 4. Пять операций

Названия описывают контракт компонента; окончательные Swift-объявления определяются в плане реализации.

| Операция | Вход | Успешный результат |
| --- | --- | --- |
| Восстановить при запуске | Нет | Завершённая привязка: `bindingId`, `publicCertificate`, `carId`; либо отсутствие привязки |
| Начать регистрацию | Нет | Сохранённая `pending`-запись и её публичное описание: `bindingId`, `publicCertificate` |
| Подписать байты | `bindingId`, точные байты | Подпись ECDSA P-256 с SHA-256 в DER |
| Завершить регистрацию | `bindingId`, подтверждённый сервером `carId` | Надёжно сохранённая `registered`-запись и её публичное описание |
| Сбросить привязку | Нет | Записи и ключи авторизации приложения удалены |

### Восстановление

Выполняется до начала авторизации. Проверяет признак установки по разделу 6, затем читает запись. Для `registered` возвращает публичное описание. Для `pending` или `resetting` завершает очистку и возвращает отсутствие привязки. Если очистка не завершилась, возвращает ошибку и не разрешает использовать эту запись для авторизации.

Операция также используется для пользовательского повтора после ошибки чтения. Повтор не запускает HTTP-запрос внутри хранилища.

### Начало регистрации

Разрешено после успешного восстановления при отсутствии записи. Создаёт ключи и новый `bindingId`, сохраняет `pending`; только после подтверждения сохранения возвращает публичное описание для запроса `pair`.

Существующая привязка молча не заменяется: сначала должна успешно завершиться операция сброса. Если создание или сохранение не удалось, публичное описание для отправки `pair` не возвращается.

### Подпись

Разрешена для актуального `bindingId` в `pending` и `registered`; для `resetting` запрещена. Клиент авторизации передаёт точные UTF-8 байты строки `<timestamp>|<rawBody>`. Хранилище подписывает их, клиент кодирует DER-подпись в Base64 и помещает в `X-Signature`.

Хранилище не сериализует JSON и не добавляет timestamp. Это сохраняет совпадение подписанных и отправленных байтов. Подпись доказывает серверу владение приватным ключом; отправки одного публичного ключа для этого недостаточно.

### Завершение регистрации

Вызывается только после получения и проверки первого JWT клиентом авторизации. Хранилище проверяет совпадение `bindingId` с текущей `pending`-записью, сохраняет `carId` и `registered`. Менеджер сессии публикует JWT только после успешного сохранения.

Повторное завершение для уже зарегистрированных тех же `bindingId` и `carId` возвращает ту же привязку. Другой идентификатор, другая машина или `resetting` дают ошибку; запись не перезаписывается. Истечение JWT не переводит `registered` в `pending`.

### Сброс

Для читаемой записи сначала сохраняет `resetting`, затем удаляет данные авторизации. Если процесс завершится после сохранения `resetting`, следующий запуск продолжит очистку.

Сброс должен работать и при некорректной записи: удаление использует принадлежность Keychain-записи приложению, а не успешное декодирование объекта. Если сохранить `resetting` невозможно, допускается завершить сброс прямым удалением. Успех сообщается только после успешного удаления или подтверждённого отсутствия данных. Если ни пометка, ни удаление не удались, сообщается ошибка; завершённый сброс не объявляется.

При отказе сброса различаются два случая:

- `resetting` сохранён, удаление не удалось: запись исключена из авторизации, повтор и следующий запуск продолжают очистку;
- ни `resetting`, ни удаление не удалось подтвердить: в текущем процессе координатор блокирует авторизацию и предлагает повторить сброс. После перезапуска хранилище читает фактически сохранённое состояние; если осталось `registered`, привязка может восстановиться. Запрет восстановления между запусками гарантируется только при сохранённом `resetting` либо удалённых данных. Дополнительный постоянный признак намерения сброса не вводится.

Удаляются все принадлежащие приложению записи авторизации, включая остатки незавершённых попыток; внутренние ссылки на прежний ключ освобождаются. Повторный сброс при отсутствии записей успешен. Очистка других приложений и серверный отзыв ключей не выполняются.

## 5. Состояния и прерывание процесса

| Событие | Сохранённое состояние после успеха |
| --- | --- |
| Создание новой привязки | `pending` |
| Получение JWT и успешное сохранение регистрации | `registered` |
| Начало очистки читаемой записи | `resetting` |
| Завершение очистки | Записи нет |

Прерывание процесса с `pending` означает новую регистрацию с QR после очистки. Прерывание с `registered` сохраняет вход через обмен ключа на JWT. Прерывание с `resetting` требует завершения удаления до нового входа.

Все операции сериализуются. Проверка идентификатора и соответствующее изменение записи выполняются без возможности вмешательства другой операции. Сброс делает прежний `bindingId` недействительным; позднее завершение регистрации или подпись для него не применяется к новой привязке. Координатор дополнительно прекращает сетевые операции и отсеивает их поздние результаты.

## 6. Переустановка и признак установки

Удаление приложения не гарантирует удаление его Keychain-записей. Поэтому при первом запуске после удаления и повторной установки самостоятельно очищаем прежнюю привязку до авторизации.

Признак установки — локальный файл в постоянном каталоге данных приложения, вне Keychain и кеша. Файл исключается из резервного копирования, чтобы восстановленный признак не выдавал другую установку за прежнюю. Ключей, JWT и данных машины в нём нет.

Порядок восстановления:

1. Проверить признак установки. При ошибке проверки вернуть ошибку локального признака: Keychain-записи не удалять, авторизацию не начинать.
2. Если наличие признака подтверждено, перейти к чтению записи привязки.
3. Только при подтверждённом отсутствии признака удалить принадлежащие приложению записи авторизации в Keychain, даже если они корректны и имеют `registered`.
4. После успешной очистки надёжно сохранить признак.
5. Вернуть отсутствие привязки; координатор показывает welcome.

При ошибке удаления или сохранения признака возвращается ошибка. Старую привязку в этом запуске не используем. После прерывания до сохранения признака очистка безопасно повторяется. Если признак потерян, это трактуется как новая установка и также требует нового QR.

Признак сохраняется при обычной отмене и перепривязке. Полный debug-сброс удаляет его вместе с остальными данными приложения. После этого следующий запуск повторяет процедуру первого запуска. Различение полного удаления приложения и восстановления после выгрузки приложения системой не требуется: решение определяется наличием признака.

## 7. Ошибки и пользовательские действия

Хранилище различает отсутствие записи, ошибку доступа/операции Keychain, некорректную запись, ошибку криптографии, ошибку локального признака и обращение к неактуальной привязке. Ошибка содержит этап и технический код, если он доступен; секретные данные в описание и диагностику не включаются.

Ошибка чтения или некорректная запись не приравниваются к отсутствию привязки. Координатор показывает общий экран ошибки с причиной и действиями:

- «Повторить» — повторить восстановление без предварительного удаления завершённой привязки;
- «Сбросить авторизацию» — после подтверждения выполнить очистку, затем вернуть на welcome для нового QR.

Подтверждение объясняет локальный сброс привязки и необходимость снова сканировать QR. Если сброс не удался, остаётся экран ошибки; новая регистрация не начинается. Для ошибки очистки повторы продолжают очистку, а не восстанавливают вход по `resetting`.

Неактуальный `bindingId` после отмены — ожидаемое отклонение позднего результата; координатор не показывает поверх нового сценария ошибку отменённой попытки. Автоматических сетевых повторов компонент не выполняет. Общие правила ошибок первичного `pair` остаются в спецификации приложения.

## 8. Связь с полным debug-сбросом

Обычный сброс этого компонента удаляет привязку и ключи авторизации. Координатор отдельно очищает JWT и текущий веб-документ; статический веб-кеш сохраняется.

Полный debug-сброс сначала останавливает операции приложения, затем очищает все принадлежащие приложению Keychain-записи, локальные файлы, UserDefaults, веб-данные и оперативную сессию. Если появятся другие секреты приложения, очистка debug должна охватить и их, а не ограничиться одной записью привязки. Хранилище участвует очисткой авторизационных данных; перечень остальных данных принадлежит общей операции сброса. Ошибка удаления запрещает объявлять полный сброс успешным.

## 9. Требования к будущей проверке

Это сценарии для плана реализации, а не отчёт о выполненных тестах:

1. Первый запуск очищает старые Keychain-записи и только затем сохраняет признак установки.
2. Ошибка проверки признака не запускает удаление Keychain и блокирует авторизацию. Ошибка очистки или записи признака также блокирует использование старой привязки; повтор восстанавливает корректный порядок.
3. Обычный перезапуск возвращает `registered`; JWT при этом на диске отсутствует.
4. Создание возвращает публичный ключ только после сохранения `pending`.
5. Прерывание с `pending` или `resetting` приводит к очистке до следующей регистрации.
6. Успешное завершение сохраняет `carId`; другое `bindingId` или другой `carId` не меняют запись.
7. Сброс и поздний ответ прежней регистрации не восстанавливают старую привязку и не изменяют новую.
8. Подпись проверяется сервером для точных байтов запроса; изменённое тело не проходит проверку.
9. Ошибка Keychain отличается от отсутствия записи; чтение некорректных данных не удаляет их автоматически.
10. Пользовательский сброс удаляет в том числе недекодируемую запись; повтор при отсутствии данных успешен.
11. Прерывание или отказ сброса не выдаются за успешную очистку. Сохранённый `resetting` приводит к продолжению очистки после перезапуска; если пометка и удаление не удались, в текущем процессе вход блокируется, а после перезапуска допускается восстановление оставшегося `registered`.
12. Приватный ключ недоступен через публичный контракт, bridge, логи и текст ошибок.
13. Переустановка требует QR; обычная перепривязка сохраняет признак установки; полный debug-сброс очищает и признак, и все Keychain-записи приложения.
