# Задание: подготовить ZDEEP WebView и bridge для iOS

Дата: 2026-10-03.

Статус: проект отдельного задания для проверки вместе со [спецификацией iOS](2026-10-03-mobile-session-design.md). Доработки выполняются в `zdeep-webview2` до начала реализации интеграции iOS. В этом задании описан контракт, а не внесённые изменения веб-репозитория.

## 1. Результат

iOS начинает загрузку веба одновременно с запуском приложения, ещё до получения JWT. Веб должен дождаться сессии, отобразить первый содержательный экран и уведомить iOS, что WebView можно показать. Во время работы JWT обновляет iOS; веб принимает новую сессию и выходит из временной ошибки авторизации без перезагрузки страницы.

Постоянное сохранение статических ассетов между запусками должно поддерживаться настройками веб-сервера. JWT и данные машины остаются привязаны к текущей сессии.

## 2. Текущее состояние

В `src/shared/session/types.ts` есть:

- `getSession(): Promise<WebviewSession>`;
- `recoverUnauthorized(): Promise<SessionRecovery>`;
- необязательный `getHostState()`;
- сессия `accessToken`, `carId`, `expiresAt`;
- результат восстановления `ready` или `terminal`.

Сигнала готовности экрана и уведомления о смене JWT нет. `src/app/session/SessionProvider.tsx` при отказе bridge или `terminal` переходит в конечное состояние и очищает сессию. `src/shared/session/resolveBridge.ts` валидирует сессию и сохраняет только три текущих поля. Apollo-клиент зависит от сессии и может пересоздаваться при её смене. Эти места нужно согласованно изменить.

Существующие `zdeep:host-event` с `lifecycle`/`refresh` и `getHostState()` сохраняют назначение. Сессионные события описаны отдельно, чтобы изменения не смешивали обновление JWT с пользовательским обновлением страницы.

Сверка с готовой инфраструктурой iOS: сейчас `WebSession.swift` внедряет только `window.ZdeepNative = {}` на старте главного документа в `.page`. Бизнесовые методы, lifecycle и события сессии нативной стороной ещё не реализованы. Они входят в iOS-задачу по этому контракту. Веб-задание проверяется на host-фикстурах/development-адаптере; готовность обоих компонентов затем проверяется совместной интеграцией.

## 3. Предлагаемый точный контракт

Версия контракта — `2`. Требуется согласованная реализация веба и нативного host. Автоматическое молчаливое принятие host без обязательных методов не допускается.

```ts
type WebviewSession = {
  accessToken: string;
  carId: string;
  expiresAt: string; // UTC ISO 8601
  revision: number; // положительное безопасное целое
};

type SessionRecovery =
  | { status: 'ready'; session: WebviewSession }
  | { status: 'unavailable'; reason: 'temporary' | 'expired' }
  | { status: 'terminal'; screen: 'session-error';
      reason: 'unavailable' | 'authorization' };

type WebviewReady = {
  sessionRevision: number;
  screen: 'content' | 'error';
};

type SessionEvent =
  | { type: 'sessionChanged'; sequence: number; revision: number }
  | { type: 'sessionExpired'; sequence: number; revision: number };

type ZdeepNativeBridge = {
  protocolVersion: 2;
  getSession(): Promise<WebviewSession>;
  recoverUnauthorized(context: { sessionRevision: number }): Promise<SessionRecovery>;
  getHostState(): Promise<HostState>;
  reportReady(ready: WebviewReady): Promise<void>;
};
```

Сессионные события доставляются через `window` как `CustomEvent('zdeep:session-event', { detail })`. `sequence` монотонно растёт в области текущего host и привязки независимо от `revision`; позволяет упорядочить смену и истечение одной и той же сессии. `revision` растёт при каждом новом JWT. В новом документе обработчики начинают новую область наблюдения; старые транспортные сообщения не допускаются нативной стороной.

Событие не содержит JWT. После `sessionChanged` веб получает актуальную сессию через `getSession()`. Подписку устанавливаем до первоначального чтения сессии. Повторные события и асинхронные ответы обрабатываются с проверкой версии; старый результат не заменяет новый. После возвращения в foreground веб сверяется с `getSession()`, даже если событие пропущено. Чтения можно объединять в одну операцию, после которой обрабатывается накопленное уведомление о более новой версии.

Транспорт каждого вызова связан с текущим документом и поколением привязки. Идентификаторы документа/попытки реализуются нативным адаптером, без необходимости помещать их в бизнесовые данные машины. `reportReady` дополнительно несёт версию использованной сессии. Метод доступен только главному frame доверенного origin.

Версия 2 относится только к бизнесовому `ZdeepNative`. У существующего USB mailbox iOS отдельный протокол версии 1, свой `sessionId` экземпляра WebKit и поле `ready` для диагностического транспорта. Веб-приложение не читает этот handshake; диагностическая готовность и `document.readyState = 'complete'` не заменяют `reportReady`. Доработка веб-контракта не требует изменения USB-протокола.

Ранняя загрузка и видимость разделены: веб может находиться в подготовленном WebView под нативным экраном. Начальная загрузка данных после JWT и `reportReady` не должны ждать пользовательской видимости документа, иначе iOS будет ждать сигнал, который веб не сможет отправить до своего показа. Если скрытый WebView не получает `requestAnimationFrame`, сигнал после фиксации первого содержательного состояния не должен навсегда блокироваться ожиданием такого callback. После раскрытия обычное управление foreground/visibility для последующего polling сохраняется.

## 4. Начальная загрузка и готовность

1. Веб подключается к внедрённому `window.ZdeepNative` и устанавливает сессионную подписку.
2. Первоначальный `getSession()` может ожидать завершения регистрации или обмена сертификата; длительное ожидание до сессии не является веб-ошибкой само по себе.
3. До действующей сессии запросы данных машины не отправляются. Статические ассеты загружаются обычным способом.
4. После сессии веб проверяет JWT-контекст, `carId`, `expiresAt` и `revision`, начинает загрузку экрана.
5. Когда первый содержательный экран фактически отрисован, вызывает `reportReady({ sessionRevision, screen })`.

`screen: 'content'` означает, что первая загрузка необходимых данных завершилась и отображается интерфейс машины. `screen: 'error'` означает, что отображается обработанный экран ошибки получения данных или приложения. Пустой контейнер, скелетон, получение JWT и завершение загрузки HTML не считаются готовностью.

Для частично успешного ответа готовность допустима, когда основной интерфейс уже отрисован, а ошибки отдельных блоков отображены в этих блоках. Не требуется ждать окончания всех последующих фоновых запросов, polling или загрузки невидимых разделов.

Сигнал отправляется после фиксации соответствующего состояния React, а не в начале запроса или перед отображением экрана. Дубли одного сигнала для документа и версии допустимы и идемпотентны. При смене сессии до первого показа готовность относится к её актуальной версии. Если начальная загрузка полностью сломалась и JS не запустился, iOS завершает ожидание собственным таймаутом.

Нативная сторона отсчитывает 60 секунд активного времени с момента, когда JWT доступен для передачи; за таймаут отвечает iOS. Веб не дублирует этот таймер и не инициирует локальный сброс сертификата. Если нативное ожидание уже завершено ошибкой или отменой, запоздавшая готовность не открывает WebView.

## 5. Упреждающее обновление JWT

iOS получает новый JWT за 120 секунд до истечения, повторяя неудачные попытки с согласованными паузами. Веб не содержит второго периодического планировщика авторизации. Несколько параллельных HTTP 401 объединяются через `recoverUnauthorized()`; нативный менеджер объединяет их с уже выполняющимся обменом. В аргументе передаётся версия токена, фактически использованного отклонённым запросом. Её фиксируем вместе с токеном при отправке запроса, а не читаем из уже обновлённой сессии после ответа.

При `sessionChanged` веб получает новый JWT через `getSession()` и обновляет источник токена для запросов. В обычном успешном обновлении для той же машины и пользователя сохраняются состояние страницы, положение прокрутки и данные Apollo; WebView и документ не перезагружаются. Пересоздание Apollo-клиента на каждой версии JWT не должно случайно очищать интерфейс.

Если веб ранее показывал временную ошибку авторизации, новый JWT переводит его в рабочее состояние и повторяет чтение данных. Автоматически повторяются только безопасные операции чтения. Операции изменения данных, чей результат неизвестен, автоматически заново не выполняются.

Веб валидирует неизменность `carId` и `userId` внутри документа. Переход к другой привязке требует нового документа со стороны iOS и очистки прежней сессии. `revision` не используется для разрешения смены пользователя в существующем документе.

## 6. Истечение и временная недоступность

Временный отказ обновления до истечения старого JWT сохраняет действующую сессию. Native не отправляет `sessionExpired` преждевременно. `getSession()` возвращает действующий токен, пока он есть, даже если плановое обновление пока не удалось.

При истечении native отправляет `sessionExpired`. Веб прекращает использование истёкшего JWT и отображает восстанавливаемую ошибку. Ошибка HTTP 401 также может начать восстановление до получения события. Обработчик всегда проверяет версию: запоздавшее истечение прежнего токена не уничтожает уже полученную новую сессию.

Вызов `recoverUnauthorized()` ожидает не более одной актуальной попытки получения токена, а не всей серии бесконечных повторов. Если действующая сессия с версией выше переданной `sessionRevision` уже есть, возвращает её сразу. Иначе присоединяется к актуальному обмену или инициирует одну попытку обновления; тот же отклонённый JWT не возвращается как успешное восстановление. Если обмен не удался, возвращает `unavailable`; ошибка отображается, а нативные периодические повторы продолжаются независимо от завершённого вызова. `getSession()` после истечения без нового токена сообщает временную недоступность, вместо возврата просроченного JWT. Первоначальное ожидание сессии до первого входа отличается от этого состояния.

`unavailable` не очищает нативную привязку, не уничтожает сессионную подписку и не навсегда блокирует provider. Последующее `sessionChanged` или сверка на foreground может восстановить экран. Старый `terminal` остаётся для несовместимого контракта, повреждённого контекста либо запрещённой смены идентичности внутри документа; временные сетевые ошибки и истечение JWT не переводятся в `terminal`.

Уже показанный WebView не запрашивает нативное скрытие при сетевой ошибке. Нативные экраны ошибок предназначены для входа и первого открытия; веб-ошибки во время работы обрабатываются внутри веб-интерфейса.

## 7. Фон, отмена и кеш

Существующие события жизненного цикла остаются источником активности приложения. После возвращения веб сверяет сессию с host и возобновляет загрузку данных, когда сессия действующая. Нативная сторона при необходимости обновляет JWT; это не повод перезагружать страницу.

Отмена или подтверждённая перепривязка завершают текущий документ с ожидающими bridge-вызовами и очищают JWT и данные машины в памяти. Следующий документ получает новую сессию и не показывает данные прежней машины. Веб не сохраняет JWT в localStorage, sessionStorage, IndexedDB, cookies, URL или постоянный кеш.

HTTP-кеш статических ассетов сохраняется. На веб-сервере нужны:

- длительное кеширование JS/CSS/изображений с версией или хешем в URL;
- проверка актуальности HTML, чтобы новая версия могла загрузиться;
- отсутствие постоянного кеширования персональных API-ответов;
- корректное обновление приложения при сохранённом кеше прежних ассетов.

Постоянное хранилище WebKit настраивается в iOS. Это задание не требует собственного сервиса офлайн-режима или гарантии хранения каждого ассета на диске.

## 8. Объём изменений в веб-репозитории

| Место | Изменение |
| --- | --- |
| `src/shared/session/types.ts` | Версия контракта, revision, reportReady, временное восстановление и типы событий |
| `src/shared/session/resolveBridge.ts` | Проверка обязательных возможностей и адаптация всех новых методов без потери полей |
| `src/shared/session/devBridge.ts` | Поддержка того же контракта в development, последовательные версии сессии |
| `src/app/session/SessionProvider.tsx` | Подписка, сверка на foreground, смена токена, восстанавливаемая ошибка и защита от гонок |
| `src/app/apollo/client.ts`, `src/app/App.tsx` | Обновление токена без случайного пересоздания всего клиента; объединение 401; безопасное восстановление чтений |
| Первый экран, экран ошибки, error boundary | reportReady после фактического отображения содержимого или обработанной ошибки |
| Конфигурация веб-хостинга | Кеширование версионированных ассетов, актуальность HTML и запрет постоянного кеша пользовательских API-ответов |

Development-адаптер реализует одинаковую бизнесовую семантику сессии и revision. Нативный reportReady в обычном браузере может быть наблюдаемой заглушкой для разработки. Production не подменяет отсутствующий контракт development-сессией.

Методы и события должны быть описаны в документации веб-репозитория. Формат диагностических сообщений не содержит JWT, QR токена, подписи и приватного ключа.

## 9. Приёмка задания

Это требования к будущей проверке, а не утверждение о выполненных изменениях.

1. При отложенном первоначальном `getSession()` статические ресурсы загружаются, GraphQL-запросов данных машины нет.
2. После передачи JWT первый экран с данными сообщает `reportReady` с правильной версией.
3. Первый обработанный экран ошибки также сообщает готовность; скелетон и пустой provider не сообщают её.
4. Новый JWT без перезагрузки документа попадает в следующие запросы, не сбрасывает экран и клиентский кеш той же машины.
5. Неудачное обновление при ещё действующем JWT не уничтожает текущую сессию.
6. Истечение или HTTP 401 показывают восстанавливаемую ошибку, а последующий JWT возвращает данные без перезапуска приложения.
7. `recoverUnauthorized()` завершается результатом одной попытки, параллельные 401 объединяются, временная ошибка не становится `terminal`.
8. Пропущенное событие восстанавливается через сверку сессии на foreground; подписка ставится до первого чтения.
9. Старые события и ответы, включая истечение прежнего JWT после получения нового, не откатывают сессию.
10. Сброс привязки и новый документ не показывают данные прежнего пользователя; смена идентичности в существующем документе отвергается.
11. Восстановление не повторяет операции изменения данных с неопределённым результатом.
12. Production проверяет контракт версии 2; development поддерживает его форму; JWT не попадает в URL, логи или постоянные веб-хранилища.
13. Реальные ответы хостинга подтверждают кеширование версионированных ассетов и актуальность HTML; новая версия открывается с прежним кешем.

Результат отдельной работы: изменения веб-репозитория, документация контракта и отчёт по этим сценариям. Передача задания сама по себе не разрешает изменения бэкенда и не заменяет письменное одобрение спецификации iOS.
