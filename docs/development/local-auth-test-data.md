# Тестовые данные авторизации на local

Дата: 2026-10-04.

Пользователь предоставил локальный метод выдачи временного QR-токена и поручил использовать его для проверок. Все проверки реализации сначала проходят на симуляторе со стендом `local`; физический iPhone используется на финальном этапе.

## Получение токена машины

| Поле | Значение |
| --- | --- |
| Метод | `POST` |
| URL | `http://localhost:4002/get-tmp-test-car-token` |
| Заголовок | `Content-Type: application/json` |
| Тело | `{"carId":"e0f1c2b3-ce9d-4e0a-95e3-fe4bf1f519f6"}` |

Успешный ответ содержит `carId`, `carToken`, `expiresIn: 600` и `expiresAt`. `carToken` — JWT машины для `pair`, а не пользовательский access token. Запрос временного токена не требует подписи мобильного ключа.

Перед каждым независимым сценарием регистрации получаем свежий токен и держим его в памяти. Не используем ранее присланный долгоживущий JWT. Не сохраняем выдаваемые токены в репозитории, отчётах, журналах или постоянных тестовых файлах.

Для симулятора тестовая подача сканирования использует ссылку формата из общей спецификации с этим `carToken`. QR для ручного сценария также строится из свежего токена; адрес из QR не заменяет настроенные адреса API или WebView.

## Цепочка проверки

1. Проверить локальный `/health`.
2. Получить временный `carToken` указанным методом.
3. Создать тестовую пару ключей P-256 и выполнить подписанный `POST /auth/mobile/pair`.
4. Проверить пользовательскую сессию и ожидаемый `carId`, не выводя access token.
5. Выполнить подписанный `POST /auth/mobile/token` с тем же ключом и проверить сохранение идентичности.

Запросы `pair` и `token` подписываются по [спецификации клиента авторизации](../superpowers/specs/2026-10-03-auth-client-design.md). Успешный `pair` создаёт настоящую привязку в локальной базе. Автоматическая очистка серверных привязок в продуктовый сценарий не входит.

Метод зависит от сохранённого ключа эмулируемой машины и совпадения её публичного ключа с записью в локальной базе. Ошибки `TEST_MACHINE_NOT_FOUND`, `CAR_NOT_FOUND` или `MACHINE_KEY_MISMATCH` означают проблему подготовки стенда; тест не заменяет ключи или данные, чтобы обойти её.

Контракт сверён с `zdeep-webview2/backend/README.md` и `backend/tmp-test-car-token.mjs`.

## Фактическая проверка

2026-10-04 Luna выполнила реальные запросы к `http://127.0.0.1:4002`:

| Запрос | Результат |
| --- | --- |
| `GET /health` | HTTP 200 |
| `POST /get-tmp-test-car-token` | HTTP 200; TTL токена машины — 600 секунд |
| `POST /auth/mobile/pair` | HTTP 200; выдан пользовательский JWT |
| `POST /auth/mobile/token` | HTTP 200; совпали пользователь и машина из `pair` |

Проверенный `carId`: `e0f1c2b3-ce9d-4e0a-95e3-fe4bf1f519f6`. Оба пользовательских JWT имеют TTL 900 секунд и audience `zdeep-webview`.

Привязка создана в локальной базе и оставлена. Одноразовый приватный ключ находился только в памяти, временный runner удалён. Код, серверные секреты и данные тестовой машины не изменялись. Это подтверждает локальный API-контракт; реализация iOS и сканирование камерой этой проверкой не подтверждены.
